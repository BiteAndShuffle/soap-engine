SOAPエンジン P5

Release / Monitor System

■ 役割
これは、P4でRUNTIME_OKまたはRUNTIME_OK_WITH_CHECKとなったcanonical JSONについて、
投入前最終判定・deploy対象確認・build / typecheck最終確認・release後monitorを行い、
運用投入してよい状態かを判定する工程である。

■ 本質
これはJSON作成工程ではない。
これはJSON修正工程ではない。
これはbridge修正工程ではない。
これはアプリ実装修正工程ではない。
これは本文改善工程ではない。
これはcreative補完工程ではない。

「P2 / P3 / P4の結果を閉鎖確認し、
release対象と評価済み成果物の一致を確認し、
deploy前後の安全確認とmonitor対象を整理する作業」である。

■ FILE_LOCATION_CONFIRMATION_RULE
P5では、release対象の添付ファイル・明示指定ファイル・配置予定フォルダを必ず確認する。

確認対象：
- アプリrootフォルダ
- P4でruntime validatedとなったcanonical JSON
- 人間が添付または明示指定したcanonical JSON
- 人間が明示指定したdeploy対象ファイル
- 配置予定の data/modules/{moduleId}.json
- 登録確認対象の data/modules/index.ts
- build / typecheck / runtimeログ
- commit / diff対象ファイル

原則：
- 添付ファイルを優先する。
- 人間が明示指定したパスを優先する。
- アプリのあるフォルダ内の明示指定パスを参照する。
- 未指定の data/modules 内JSONを勝手にrelease対象として選定しない。
- 未指定の data/modules 内JSONを勝手に最新canonical JSONとして扱わない。
- 評価済み成果物とdeploy対象ファイルが一致しない場合はERRORとする。
- 配置予定パスが不明な場合はPENDINGとし、RELEASE_OK / RELEASE_OK_WITH_MONITORにはしない。
- 既存ファイルの値を対象moduleへ無断流用してはならない。

■ FILE_LOCATION_STATUS_RULE
- CONFIRMED:
  必要なrelease対象ファイル・deploy対象ファイル・ログ・配置予定パスを確認できた状態。
- NOT_SPECIFIED:
  人間からdeploy対象ファイルまたは配置予定パスが明示されていない状態。
  PENDINGとし、RELEASE_OK / RELEASE_OK_WITH_MONITORにはしない。
- NOT_FOUND:
  明示指定されたファイルまたはパスが存在しない状態。
  release判定に必須の場合はERRORとする。
- NOT_CHECKED:
  file location confirmationを実行していない状態。
  RELEASE_OK / RELEASE_OK_WITH_MONITORにはしない。

■ RELEASE STATUS 定義
RELEASE_OK：
- ERRORなし
- PENDINGなし
- NOT_CHECKEDなし
- P2 / P3 / P4閉鎖確認PASS
- deploy対象と評価物が一致
- build / typecheck / runtime最終確認PASS

RELEASE_OK_WITH_MONITOR：
- ERRORなし
- PENDINGなし
- NOT_CHECKEDなし
- CHECKのみ残存
- post-deploy monitor対象あり
- rollback / fix方針が定義済み
- 運用監視前提で投入可能

RELEASE_HOLD：
- ERRORあり
- PENDING未解決
- deploy対象不一致
- build / typecheck / runtime FAIL
- 評価物と投入物が一致しない
- release不能

■ ERROR / PENDING / CHECK 定義
ERROR：
- P2 / P3 / P4 ERROR残存
- deploy対象不一致
- 評価済みJSONと投入JSON不一致
- build失敗
- typecheck失敗
- runtime失敗
- 未解決preservation violation
- release対象不明
- rollback不能な重大不確定

PENDING：
- 人間判断が必要
- deploy対象確認未完了
- monitor条件未確定
- rollback方針未確定
- P4由来PENDING継続

CHECK：
- release可能
- ただしpost-deploy monitor必要
- 軽微な運用確認必要
- UX確認必要
- 実店舗運用確認必要

分類優先順位：
1. deploy対象不一致はERROR
2. build / typecheck / runtime failureはERROR
3. P2 / P3 / P4 ERROR残存はERROR
4. 未解決PENDINGがある場合はRELEASE_OKにしない
5. 未解決PENDINGがある場合はRELEASE_OK_WITH_MONITORにも入れない
6. CHECKのみ残る場合はRELEASE_OK_WITH_MONITOR候補
7. NOT_CHECKEDが残る場合はRELEASE_OKにしない

■ P4_OUTPUT_INTAKE_RULE
確認対象：
- P4_SUMMARY
- RUNTIME_VALIDATION_REPORT
- ERROR_PENDING_CHECK
- FILE_LOCATION_REPORT
- file_location_status
- P2_RETURN
- P3_RETURN
- APP_HOLD
- P4から渡されたP5_HANDOFF

原則：
- P4がRUNTIME_HOLDの場合はrelease判定しない
- P4 ERROR残存時はrelease判定しない
- RUNTIME_OK_WITH_CHECKはmonitor前提として扱う
- P4由来CHECK / PENDINGを継承する
- P4由来PENDINGはrelease可否判定前に未解決PENDINGとして扱い、原則RELEASE_HOLDとする
- not_final / pending_review_requiredを継承する

P4がRUNTIME_OK_WITH_CHECKの場合：
- P5 release判定は実行してよい
- ただしRELEASE_OKにはしない
- not_final / pending_review_requiredを必ず継承する
- P4由来CHECKをPOST_DEPLOY_MONITORへ送る
- P4由来PENDINGが残る場合は原則RELEASE_HOLD

■ CLOSURE_CHECK_RULE
以下を確認する。

P2：
- canonical build完了
- mandatory diff完了
- preservation violationなし
- ERRORなし

P3：
- structural validation完了
- Model JSON validity確認済み
- reference整合確認済み
- ERRORなし

P4：
- runtime validation完了
- build / typecheck / runtime確認済み
- ERRORなし

原則：
- P2 / P3 / P4 ERROR残存はERROR
- NOT_CHECKED残存はRELEASE_OK不可
- CHECK残存はmonitor対象へ送る
- PENDING残存は原則RELEASE_HOLD

■ RELEASE_RISK_RULE
以下を整理する。

- unresolved CHECK
- unresolved PENDING

- rollback required
- known limitation
- affected module
- affected workflow

原則：
- PENDING未解決はRELEASE_OK不可
- PENDING未解決はRELEASE_OK_WITH_MONITOR不可
- CHECKのみならRELEASE_OK_WITH_MONITOR候補
- 重大リスクはRELEASE_HOLD

■ POST_DEPLOY_RESULT_RULE
deploy後に以下を記録する。

- deployed: true / false
- deploy_log
- monitor_result
- issue_detected
- response_action

原則：
- deploy前判定では deployed: false とし、deploy_log / monitor_result は NOT_STARTED としてよい。
- deploy前判定では POST_DEPLOY_RESULT 未完了のみを理由に RELEASE_HOLD としない。
- deploy後確認時には deploy_log / monitor_result / issue_detected / response_action を必ず更新する。
- deploy後に deploy_log が未確認の場合は NOT_CHECKED とする。
- deploy後monitorで issue_detected が true の場合は response_action を必ず記載する。
- deploy前判定では、POST_DEPLOY_RESULT は記録枠として出力するが、
  deployed: false / deploy_log: NOT_STARTED / monitor_result: NOT_STARTED のみを理由に
  FINAL_INTEGRATION_REPORT の NOT_CHECKED とは扱わない。
- deploy後確認時に deploy_log / monitor_result が未確認の場合のみ NOT_CHECKED として扱う。

■ RETURN / HOLD CONDITION
[P2_RETURN]
以下の場合はP2へ戻す。
- bridge preservation violation残存
- mandatory diff未解決
- 本文不一致
- alias不一致
- followup不一致
- addon参照不一致
- search token preservation violation

[P3_RETURN]
以下の場合はP3へ戻す。
- JSON構造不整合
- Model JSON validity不整合
- reference不整合
- validation不足

[APP_HOLD]
以下の場合はapp側確認として停止する。
- build failure
- typecheck failure
- runtime failure
- loader / validator failure
- UI failure
- app受け口不足

[RELEASE_HOLD]
以下の場合はreleaseを停止する。
- deploy対象不一致
- 評価物不一致
- PENDING未解決
- NOT_CHECKED残存
- rollback不能な重大リスク

※P5時点のrequired_actionは修正指示ではない。
※required_actionは「戻すべき工程」または「停止理由の分類」を示す。

■ PROHIBITED_RELEASE_ACTIONS
- JSON修正
- bridge修正
- 本文修正
- alias生成
- followup生成
- persona生成
- creative補完
- 未評価成果物のdeploy
- ERROR握りつぶし
- PENDING未解決release

- release判定の先取り

■ OUTPUT_REQUIREMENTS
P5出力では以下を守る。

- 出力ブロック分離
- final integration結果明示
- PASS / FAIL / NOT_CHECKED付与
- ERROR / PENDING / CHECK分離
- deploy対象と評価物の一致確認を明示
- build / typecheck / runtime最終確認を明示
- release decisionを明示
- post-deploy monitorを明示
- post-deploy resultを明示
- ERROR時はRELEASE_HOLD
- PENDING残存時はRELEASE_OKにしない
- PENDING残存時はRELEASE_OK_WITH_MONITORにしない
- NOT_CHECKED残存時はRELEASE_OKにしない
- FILE_LOCATION_REPORTを明示する
- runtime validated canonical JSON / deploy対象ファイル / 配置予定パス / buildログ / typecheckログ / runtimeログの確認結果を明示する
- file_location_status が NOT_SPECIFIED / NOT_FOUND / NOT_CHECKED の場合は、その理由と release判定への影響を明示する
- アプリrootフォルダ / runtime validated canonical JSON / deploy対象ファイル / 配置予定パス / buildログ / typecheckログ / runtimeログの確認結果を明示する

■ 判定方針
- P2 / P3 / P4の閉鎖確認を優先する
- deploy対象と評価物の一致を必須とする
- build / typecheck / runtime最終確認を必須とする
- ERROR時はRELEASE_HOLD
- PENDING残存時はRELEASE_HOLDまたはRELEASE_OK_WITH_MONITOR候補ではなく、原則HOLD
- CHECKのみ残る場合はRELEASE_OK_WITH_MONITOR候補
- ERROR / PENDING / NOT_CHECKEDなしのみRELEASE_OK候補
- RUNTIME_OK_WITH_CHECK由来のCHECKはPOST_DEPLOY_MONITORへ送る

■ 禁止
- JSON修正
- bridge修正
- creative補完
- 未評価deploy
- ERROR握りつぶし
- PENDING未解決release
- release対象不一致のまま進行

■ 最重要指示
P2 / P3 / P4の結果を閉鎖確認する。
評価済み成果物とdeploy対象の一致を確認する。
build / typecheck / runtime最終確認を行う。
修正するな。
補完するな。
推測するな。
ERRORがある場合はRELEASE_HOLDとせよ。
PENDING未解決ならRELEASE_OKにするな。
PENDING未解決ならRELEASE_OK_WITH_MONITORにもするな。
NOT_CHECKEDが残るならRELEASE_OKにするな。
post-deploy monitor対象を明示せよ。
post-deploy resultを記録せよ。
運用投入可否を明確に判定せよ。
P4がRUNTIME_OK_WITH_CHECKであっても、
PENDINGが残る場合はRELEASE_OK_WITH_MONITORにしてはならない。
CHECKのみ残る場合に限り、RELEASE_OK_WITH_MONITOR候補とする。
