SOAPエンジン P3 Structural Validation System v1.1

Structural Validation System
■ 役割
これは、P2で構築されたcanonical JSONが、
P0-A / P0-B / P0-C / P1 / P2の定義に照らして、
JSON構造・Model JSON準拠・参照整合・preservation再確認の観点で成立しているかを検証する工程である。
■ 本質
これはJSON修正工程ではない。
これはJSON再設計工程ではない。
これはアプリ実装修正工程ではない。
これはruntime確認工程ではない。
これはbuild / typecheck実行工程ではない。
これは本文改善工程ではない。
「P2で構築されたcanonical JSONを対象に、
構造妥当性・型整合・参照整合・Model JSON準拠・P2 preservation違反の残存有無を確認し、
P4へ渡せる状態かを判定する作業」である。

2. P0-B出力

4. P1出力

   ※任意。ただし存在する場合は優先参照する。

   P3 structural validation を実行してよい。
7. 人間が添付または明示指定した最新Model JSON
   ※型確認が必要な場合は、STANDARD_REFERENCE_PATHSの lib/types.ts 等を構造確認用に参照してよい
8. 必要に応じて人間が添付または明示指定した既存canonical JSON

※P3ではJSONを修正しない。

■ STRUCTURE STATUS 定義
STRUCTURE_OK：
- ERRORなし
- PENDINGなし
- CHECKなし
- NOT_CHECKEDなし
- 必須構造・参照整合・preservation recheckがPASS
STRUCTURE_OK_WITH_CHECK：
- ERRORなし
- JSONとして成立
- preservation違反なし
- 未解決PENDINGなし
- CHECKのみ残る
- P4確認対象が残る
STRUCTURE_HOLD：
- ERRORあり
- mandatory diff FAIL
- P2 preservation violation再検出
- JSONとして成立しない
■ ERROR / PENDING / CHECK 定義
ERROR：
- commonSearchTokens / formulationSearchTokens が aliases / normalizedAliases / aliasToBrand / search aliases へ展開された状態
- bridgeに明示された commonSearchTokens / formulationSearchTokens / search token系matchPolicy が canonical JSON に反映されていない状態
- bridge未明示の search token が推測生成された状態
- Model JSON必須構造欠落
- 型不一致
- root必須key欠落
- scenario / addon identity破壊
- 参照先欠落
- followupRef不整合
- addon参照不整合
- brandCatalog / aliasToBrand不整合
- expressModes参照不整合
- P2 preservation violation再検出
- mandatory diff FAIL
- JSONとして成立しない状態
- drug.nameAliases と drug.search.nameAliases が不一致の状態
- addons.orderPresets キーが欠落している状態
- addons.orderPresets が object 型以外である状態
PENDING：
- Model JSON / JSON RULE / APP RULE間の前提不一致
- 格納先解釈が未確定
- 人間判断が必要
- P2から未解決のPENDINGが継続
- Express / thirdPanel方針未確定
- persona構造の扱い未確定
未解決PENDINGが残る場合は、STRUCTURE_OK_WITH_CHECKではなくSTRUCTURE_HOLD候補とする。
ただし、P2由来のDEFER_CANDIDATEで、P3時点では構造成立を妨げず、P4/P5へ明示的に引き継げるものはCHECKとして扱う。
CHECK：
- commonSearchTokens / formulationSearchTokens の検索runtime確認が必要
- multi-token AND検索 / formulation token検索のapp受け口確認が必要
- search token の index.searchableText / index.normalizedTokens 反映仕様確認が必要
- search token を index に反映しない場合でも、検索エンジンが drug.search.commonSearchTokens / formulationSearchTokens を参照できるか確認が必要
- JSONとして成立する
- Model JSON必須構造は満たす
- preservation違反ではない
- ただしP4 runtime / app compatibility確認が必要
- app受け口確認が必要
- build / typecheck確認が必要
- UI / search / merge / Express / thirdPanel確認が必要
分類優先順位：
1. JSONとして成立しない場合はERRORを優先する
2. P2 preservation violationを含む場合はERRORを優先する
3. mandatory diffがFAILの場合はERRORを優先する
4. 構造判断が未確定で、ERROR未発生の場合はPENDINGとする
5. JSONとして成立し、preservation違反もないが後続確認が必要な場合はCHECKとする
6. NOT_CHECKEDが残る場合はSTRUCTURE_OKにしない

■ P2_OUTPUT_INTAKE_RULE
P2 validation package 不在に起因する NOT_PROVIDED は、
P3責務内の NOT_CHECKED とは区別する。
P2 mandatory diff結果が NOT_PROVIDED の場合でも、
bridge原稿 / 最新Model JSON / build済canonical JSON から
P3責務範囲で preservation recheck を実施できる場合、
NOT_CHECKEDとは扱わない。
NOT_CHECKED とするのは、
P3責務内の構造確認・参照確認・preservation再確認を実施できなかった項目に限定する。
P2出力を受け取る。
確認対象：
- P2_SUMMARY
- OUTPUT_JSON
- MANDATORY_DIFF_REPORT
- ERROR_PENDING
- CHECK_ITEMS
- REFERENCE_USAGE_REPORT
- P3_HANDOFF
原則：
- P2がBUILD_STOPPEDの場合は、P3 validationを続行しない
- P2にERRORが残る場合は、P3 validationを続行しない
- P2がBUILD_OK_WITH_PENDINGの場合は、NOT_FINALとして扱う
- P2のNOT_CHECKED項目を引き継ぐ
- P2の本文変更なし確認を再確認対象にする
P2がBUILD_OK_WITH_PENDINGの場合：
- P3 structural validationは実行してよい
- P2由来PENDINGを継承する
- P3_SUMMARYはSTRUCTURE_OKにしない
- 未解決PENDINGが残る場合はSTRUCTURE_HOLD候補とする
- not_final / pending_review_requiredを必ず true として継承する
- PENDINGがP3時点でCHECKへ再分類可能な場合のみ、P4_HANDOFF対象とする
- PENDINGが未解決のまま残る場合は、P4_HANDOFFを作成しない
P2がBUILD_OKの場合：
- P3 structural validationを実行する
- ERROR / PENDING / CHECK / NOT_CHECKEDがなければ、P3_SUMMARYはSTRUCTURE_OK候補とする
- not_final / pending_review_required は false として扱う
P2がBUILD_OK_WITH_CHECKの場合：
- P3 structural validationは実行してよい
- P2由来CHECKをP3確認対象またはP4_HANDOFF対象として継承する
- ERROR / PENDINGがなければ、P3_SUMMARYはSTRUCTURE_OK_WITH_CHECK候補とする
- not_final / pending_review_required は false のまま扱う
- CHECKのみを理由にSTRUCTURE_HOLDへ分類しない
P2 validation package が存在しない場合：
- P2 validation package 不在のみを理由として STRUCTURE_HOLD / PENDING / NOT_CHECKED にしてはならない
- bridge原稿 / 最新Model JSON / build済canonical JSON から、P3責務範囲の structural validation / preservation recheck を実行してよい
- P2 mandatory diff結果は NOT_PROVIDED として扱い、P3で再確認可能な preservation 項目を再検証する
- P2由来CHECK / PENDINGが不明な場合は、P3で検出した項目のみ ERROR / PENDING / CHECK として分類する
- P2 validation package 不在は REFERENCE_USAGE_REPORT に記録する
P2 validation package が存在しない場合
p2_build_status:
- NOT_PROVIDED
として扱う

■ 判定方針
- Model JSON準拠を確認する
- P0-A/B/CおよびP1/P2に従う
- P2 preservation violationを再検出する
- JSON correctness / model validityを確認する
- runtime / app compatibilityはP4へ渡す
- deterministic修正は行わない
- 不明点は推測せずPENDINGにする
- CHECKはP4確認対象として扱う
- ERRORが存在する場合はSTRUCTURE_HOLDとする
- 未解決PENDINGが残る場合はSTRUCTURE_HOLD候補とする
- ただし、P2由来のDEFER_CANDIDATEでP3時点の構造成立を妨げず、P4/P5へ明示的に引き継げるものはCHECKとして扱う
- CHECKのみの場合はSTRUCTURE_OK_WITH_CHECK候補とする
- ERROR / PENDINGなし、かつNOT_CHECKEDなしの場合のみSTRUCTURE_OK候補とする
- P2がBUILD_OK_WITH_PENDINGの場合はSTRUCTURE_OKにしない
- ERRORなし
  PENDINGなし
  CHECKあり
  の場合は STRUCTURE_OK_WITH_CHECK候補とする
- CHECKが残る場合は
  STRUCTURE_OKへ分類してはならない
- CHECKのみを理由に
  STRUCTURE_HOLDへ分類してはならない
P3責務外のruntime / build / typecheck / UI / search / compose未確認は、
NOT_CHECKEDではなくCHECKとしてP4_HANDOFFへ送る。
P3でNOT_CHECKEDとするのは、
P3責務内の構造確認・参照確認・preservation再確認を実施できなかった項目に限定する。
