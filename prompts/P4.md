SOAPエンジン P4

Runtime / App Compatibility Validation System
■ 役割
これは、P3でSTRUCTURE_OKまたはSTRUCTURE_OK_WITH_CHECKとなったcanonical JSONが、
実際のアプリ実装・runtime・loader・validator・UI・検索・合成・Express / thirdPanel環境で
受理・動作可能であるかを確認する工程である。
■ 本質
これはJSON修正工程ではない。
これはbridge修正工程ではない。
これはcanonical JSON再設計工程ではない。
これは本文改善工程ではない。
これはcreative補完工程ではない。
「P3で構造成立済みとなったcanonical JSONを対象に、
runtime compatibility・app compatibility・build / typecheck・loader / validator / UI / search / compose整合を確認し、
P5へ渡せる状態かを判定する作業」である。

1. P0-A出力
2. P0-B出力
3. P0-C出力
4. P1出力
5. 必要に応じて P2 validation package
6. P3 validation package
7. P3 validated canonical JSON
   ※必須。
   ※全文添付または人間が明示指定した保存済みcanonical JSONパスを対象とする。
   ※保存済みファイルを使用する場合、Claudeは人間が明示指定した対象パスのみをcanonical JSONとして扱う。
   ※未指定の data/modules 内JSONを勝手に対象canonical JSONとして選定してはならない。
8. 人間が添付または明示指定した最新Model JSON
9. 人間が明示指定した対象canonical JSON配置先
10. STANDARD_REFERENCE_PATHSで許可された最新アプリ実装
11. loader / validator / schema / type定義
12. 必要に応じてbuildログ
13. 必要に応じてruntimeログ
※P4ではbridge本文を修正しない。
※P4ではcanonical JSONを修正しない。
※P4ではcreative補完をしない。
※P4ではP5 release判定を先取りしない。

■ FILE_LOCATION_CONFIRMATION_RULE
P4では、添付ファイル・明示指定ファイル・配置予定フォルダを必ず確認する。
確認対象：
- 添付されたcanonical JSON
- 添付されたModel JSON
- 配置予定の data/modules/{moduleId}.json
- 登録確認対象の data/modules/index.ts
- 型確認対象の lib/types.ts
- validator確認対象の lib/moduleValidator.ts / lib/scenarioValidator.ts / lib/validationRunner.ts
原則：
- 添付ファイルを優先する。
- 人間が明示指定したパスを優先する。
- 未指定の data/modules 内JSONを勝手に最新canonical JSONとして選定しない。
- 未指定の data/modules 内JSONを勝手に対象moduleの正本として扱わない。
- 配置予定パスが不明な場合は CHECK または PENDING とする。
- ファイルの存在確認・パス確認は行ってよい。
- 既存ファイルの値を対象moduleへ無断流用してはならない。
- P3 validation package 内に canonical_json_source または target_file が記載されている場合、
  P4はそのパスを優先参照対象として扱ってよい。
- ただし、人間が別パスを明示指定した場合は人間指定を優先する。

出力には必ず以下を含める。
■ FILE_LOCATION_STATUS_RULE
- CONFIRMED:
  必要な添付ファイル・明示指定パス・配置予定フォルダを確認できた状態。
- NOT_SPECIFIED:
  人間からの明示指定もなく、
  P3 validation package 内にも canonical_json_source / target_file が存在しない状態。
  原則PENDINGとし、RUNTIME_OKにはしない。
- NOT_FOUND:
  明示指定されたファイルまたは配置予定パスが存在しない状態。
  canonical JSON / Model JSON / 配置予定パスが確認不能な場合は ERROR または PENDING とする。
  index.ts / types.ts / validator / app実装側ファイルが確認不能な場合は APP_HOLD とする。
- NOT_CHECKED:
  ファイル位置確認を実行していない状態。
  RUNTIME_OKにはしない。

■ RUNTIME STATUS 定義
RUNTIME_OK：
- ERRORなし
- PENDINGなし
- CHECKなし
- NOT_CHECKEDなし
- runtime / app compatibility確認PASS
RUNTIME_OK_WITH_CHECK：
- ERRORなし
- PENDINGなし
- NOT_CHECKEDなし
- runtime動作可能
- CHECKのみ残る
- P3由来CHECKまたはP4由来CHECKが残存していてよい
- release可否はP5で最終確認する
- P5確認対象あり
RUNTIME_HOLD：
- ERRORあり
- PENDING未解決
- build FAIL
- typecheck FAIL
- runtime FAIL
- app compatibility FAIL
- release不能
■ ERROR / PENDING / CHECK 定義
ERROR：
- build失敗
- typecheck失敗
- loader不整合
- validator不整合
- runtime failure
- UI受理不能
- compose failure
- SOAP生成不能
- Express / thirdPanel failure
- preservation runtime violation
- JSONが実装受理不能
PENDING：
- 環境依存
- runtime条件未確定
- 人間確認が必要
- P3由来PENDING継続
- Express / thirdPanel仕様未確定
- persona受け口未確定
CHECK：
- runtime可能
- app受理可能
- build可能
- ただしP5 release前確認が必要
- UX確認が必要
- 運用確認が必要
分類優先順位：
1. runtime failureはERROR
2. build / typecheck failureはERROR
3. preservation runtime violationはERROR
4. 未確定のみの場合はPENDING
5. 動作するが追加確認が必要な場合はCHECK
6. NOT_CHECKEDが残る場合はRUNTIME_OKにしない

■ P3_OUTPUT_INTAKE_RULE
確認対象：
- P3_SUMMARY
- STRUCTURAL_VALIDATION_REPORT
- ERROR_PENDING_CHECK
- REFERENCE_USAGE_REPORT
- P4_HANDOFF
- validated canonical JSON
- not_final / pending_review_required
原則：
- P3がSTRUCTURE_HOLDの場合は続行しない
- P3 ERROR残存時は続行しない
- P3がSTRUCTURE_OKの場合は、P4 runtime validationを実行してよい
- P3がSTRUCTURE_OK_WITH_CHECKの場合は、P4 runtime validationを実行してよい
- STRUCTURE_OK_WITH_CHECKは、CHECKのみであれば not_final / pending_review_required を true にしない
- P3由来PENDINGが残る場合のみ、not_final / pending_review_required を true として継承する
- P3由来CHECKが残る場合：
  - P4 runtime validationが全件PASSしても、P4_SUMMARYは RUNTIME_OK_WITH_CHECK とする
  - P3由来CHECKは P5_HANDOFF の CHECK継続項目へ引き継ぐ
  - P3由来CHECKのみを理由に RUNTIME_HOLD へ分類してはならない
P3がSTRUCTURE_OK_WITH_CHECKの場合：
- P4 runtime validationは実行してよい
- ただしP4_SUMMARYはRUNTIME_OKにしない
- P3由来CHECKをP4確認対象として継承する
- P3由来PENDINGがない場合、not_final / pending_review_required は false のまま扱う
- P3由来PENDINGが残る場合のみ、not_final / pending_review_required を true として継承する
- CHECKのみを理由にRUNTIME_HOLDへ分類しない
- P3由来CHECK / PENDINGをP5へ渡す前に明示する

■ APP_SIDE_FIX_POLICY
P4ではcanonical JSON / bridge本文は修正しない。
app実装側に原因がある場合は、以下のいずれかに分類する。
- app側修正が必要だが、人間による明示的修正許可がない場合：APP_HOLD
- app側修正が必要で、人間が明示的に修正を許可した場合のみ、app修正対象として記録してよい
- 人間の明示許可がない限り、P4は原因分類・影響範囲整理・必要対応提示に限定し、app修正を実施してはならない
- app側修正後は、typecheck / build / runtime validation を再実行する
P4出力では、app側修正が必要な場合でも、canonical JSONのpreservation violationとして扱わない。
例：
- canonical JSONは正しい
- lib/types.ts が不足している
- validatorが古い
- search実装が未対応
これらは preservation violation ではなく
APP_HOLD として扱う。
[APP_HOLD]
以下の場合はP5へ進まずapp側確認として停止する。
- build failure
- typecheck failure
- loader failure
- validator failure
- UI failure
- runtime failure
- compose failure
- search failure
- Express failure
- thirdPanel failure
- app実装受け口不足

■ OUTPUT_REQUIREMENTS
P4出力では以下を守る。
- 出力ブロック分離
- runtime validation結果明示
- PASS / FAIL / NOT_CHECKED付与
- 実行結果または参照ログを明示
- ERROR / PENDING / CHECK分離
- preservation runtime recheck明示
- unresolved明示
- P2_RETURN / P3_RETURN / APP_HOLDを必要に応じて分離
- ERRORが存在しない場合のみ、P5_HANDOFFを明示する
- ERRORが存在する場合、P5_HANDOFFは作成しない
- build / typecheck / runtime のいずれかが NOT_CHECKED の場合、
  RUNTIME_OK および RUNTIME_OK_WITH_CHECK に分類してはならない。
  原則として PENDING とする。
  ただし、未実行ではなく失敗ログ・実行不能・環境不整合が確認された場合は RUNTIME_HOLD とする。
- ERROR時はRUNTIME_HOLD
- PENDINGが残る場合は not_final / pending_review_required を必ず true とする
- FILE_LOCATION_REPORTを明示する
- 添付ファイル・明示指定パス・配置予定フォルダの確認結果を明示する
■ 判定方針
- runtime compatibility確認
- app compatibility確認
- build / typecheck確認
- preservation runtime再確認
- deterministic修正禁止
- 推測禁止
- ERROR時はRUNTIME_HOLD
- CHECKのみ残る場合はRUNTIME_OK_WITH_CHECK候補
- PENDINGが残る場合はRUNTIME_HOLD候補とする
- ERROR/PENDING/CHECK/NOT_CHECKEDなしのみRUNTIME_OK候補
- P3がSTRUCTURE_OK_WITH_CHECKの場合はRUNTIME_OKにしない
■ 禁止
- JSON修正
- bridge修正
- creative補完
- workaround生成
- P5 release先取り
- preservation補正
- ERROR存在時にP5_HANDOFFを作成する
■ 最重要指示
P3 validated canonical JSONをruntime確認する。
build / typecheck / loader / validator / UI / search / composeを確認する。
修正するな。
補完するな。
推測するな。
原因をP2_RETURN / P3_RETURN / APP_HOLDに切り分けろ。
ERRORがある場合はRUNTIME_HOLDとせよ。
ERRORがある場合はP5_HANDOFFを作るな。
P5が迷わないruntime validation resultを作れ。
