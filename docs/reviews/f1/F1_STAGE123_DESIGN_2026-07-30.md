## 1. Stage 1 — 計測スクリプトの具体案

### 1.1 設計方針: サーバ起動を必須にしない

初期 HTML の実測にはサーバ起動が必要だが、CI・日常運用で毎回起動するのは重い。**成長の主因は `ALL_MODULES` のシリアライズ量であり、これはサーバなしで決定論的に計測できる。**

実測による裏付け:

| 測定対象 | 値 |
|---|---|
| `JSON.stringify(ALL_MODULES)` minified | 3,584,368 B |
| 実測 初期 HTML | 3,949,946 B |
| 差分（アプリシェル＋エスケープ） | 365,578 B（**モジュール数に依存しない固定オーバーヘッド**） |

したがって **minified バイト数を主指標**とし、HTML 実測は任意の追加確認とする。

| 1 モジュールあたり平均 | 総量 ÷ 件数 | 新規モジュールが平均から外れていないかの検知 |
| 300 モジュール換算 | 平均 × 300 | 着手判断の材料 |

### 1.4 しきい値の扱い（Owner 判断事項 → §11 D-S1-1）

**しきい値超過を FAIL（exit 1）にするか WARN（exit 0）にするかは Owner 判断とする。** 設計としては次を推奨する。

- **WARN（exit 0）**で開始する。理由: `docs/VALIDATOR_STANDARD.md` §5 の禁止基準「ルールを機械的に適用したとき、正当な将来データを ERROR にする可能性があるなら Validator に入れない」と同じ論理。モジュール追加は正当な行為であり、それを FAIL にすると開発が止まる
- しきい値は「超えたら Owner が着手判断をする合図」として機能させる

### 1.5 実行経路の登録

```
package.json
+ "measure:payload": "npx tsx scripts/measure-payload.ts"
```

`prompts/vNext/PN8-Build-Runtime-Release.md` または `docs/IMPLEMENTATION_CHECKLIST.md` に確認項目を追加する（**どちらへ置くかは §11 D-S1-2**）。

- PN8 は「新規モジュール追加時の release 判定」→ モジュール追加のたびに計測される
- IMPLEMENTATION_CHECKLIST は「実装後に毎回行う標準検証」→ 全変更で計測される

**PN8 を推奨する。** 配信量が増えるのはモジュール追加時であり、`lib/` の修正時に毎回測る必要はない。

## 2. Stage 2 — キャッシュヘッダ変更案

### 2.1 現状（実測）

```js
// next.config.js L36-52
...(!isStaticExport && {
  async headers() {
    return [
      {
        source: '/(.*)',           // ← 全経路に適用
        headers: [
          { key: 'Cache-Control', value: 'no-store, no-cache, must-revalidate, proxy-revalidate' },
          { key: 'Pragma', value: 'no-cache' },
          { key: 'Expires', value: '0' },
        ],
      },
    ]
  },
}),
```

実測結果: `/` と `/_next/static/chunks/webpack-*.js` の**両方**に `no-store` が付与されている。

### 2.2 変更案

```js
...(!isStaticExport && {
  async headers() {
    return [
      // ① 静的資産: ファイル名にコンテンツハッシュを含むため内容不変。長期キャッシュ可
      {
        source: '/_next/static/:path*',
        headers: [
          { key: 'Cache-Control', value: 'public, max-age=31536000, immutable' },
        ],
      },
      // ② それ以外（HTML / RSC ペイロード）: 従来どおりキャッシュ禁止
      //    Vercel Edge/CDN が HTML をキャッシュしないよう強制する意図を維持する
      {
        source: '/((?!_next/static).*)',
        headers: [
          { key: 'Cache-Control', value: 'no-store, no-cache, must-revalidate, proxy-revalidate' },
          { key: 'Pragma', value: 'no-cache' },
          { key: 'Expires', value: '0' },
        ],
      },
    ]
  },
}),
```

### 2.3 設計上の注意

| 論点 | 判断 |
|---|---|
| **元の設計意図を壊さないか** | 壊さない。コメント「Vercel Edge/CDN がレスポンスをキャッシュしないよう強制」の対象は HTML（RSC ペイロードを含む）であり、②で維持される |
| **negative lookahead を使う理由** | Next.js は**マッチした全ルールのヘッダを適用**する。`source: '/(.*)'` を残すと ① と競合するため、②の対象から `_next/static` を除外する |
| **`public/` 配下（`persona-icon.webp`）** | ②の対象に残る（`no-store`）。コンテンツハッシュを持たないため保守的にキャッシュしない。**変更しない** |
| **`/_next/image`** | 本プロジェクトは画像最適化を使用していない（`next.config.js` の `images.unoptimized` は静的 export 時のみ）。対象外 |
| **静的 export 時** | `headers()` は `output: 'export'` では機能しない（Next.js 仕様）。既に `!isStaticExport` で分岐済みのため影響なし |

### 2.4 効果（実測に基づく見積り）

| | 現状 | 変更後 |
|---|---|---|
| 初回ロード | HTML 326 KB (gzip) + 静的資産 920 KB | 同じ |
| **2 回目以降** | **HTML 326 KB + 静的資産 920 KB を再取得** | **HTML 326 KB のみ**（静的資産はブラウザキャッシュ） |

初回は変わらない。**2 回目以降の静的資産取得が消える。**

## 3. Stage 3 — loader interface の具体的な型

### 3.1 設計原則: 同期のみ・加算的導入

Stage 3 の目的は**接続点を作ること**であり、挙動を変えることではない。したがって:

- **同期メソッドのみ**を定義する（`Promise` を導入しない）
- `ALL_MODULES` の export は**そのまま維持**する（テスト 37 箇所が無改修で通る）
- loader は `ALL_MODULES` を包む薄い層として実装する
- **非同期化は Stage 4 で加算的に追加**する（interface の破壊的変更にしない）

### 3.2 型定義（新規 `lib/moduleRegistry.ts`）

```ts
import type { ModuleData } from './types'
import type { SearchEntry } from './search'

/**
 * モジュールデータへのアクセスを抽象化する registry。
 *
 * Stage 3 の実装（BundledModuleRegistry）は全モジュールを同梱前提で同期解決する。
 * Stage 4 以降、SaaS 向けに manifest + 遅延取得を行う実装を追加する際は、
 * 本 interface へ非同期メソッドを**加算的に**追加する（既存メソッドは変更しない）。
 */
export interface ModuleRegistry {
  /** 登録済み moduleId の一覧（登録順） */
  listModuleIds(): readonly string[]

  /** moduleId から 1 件取得。未登録は undefined */
  getModule(moduleId: string): ModuleData | undefined

  /**
   * 全モジュールを取得（登録順）。
   * Stage 3 では ALL_MODULES と同一の参照・同一の順序を返す。
   * Stage 4 以降、SaaS 実装ではこのメソッドを提供しない可能性があるため、
   * 新規コードは可能な限り getModule / listModuleIds を使う。
   */
  getAllModules(): readonly ModuleData[]

  /**
   * 検索インデックスを取得。
   * Stage 3: 全モジュールから buildSearchIndex で構築（現行と同一）。
   * Stage 4: 2 層 manifest から構築へ差し替える（← 差し替え接続点）
   */
  getSearchIndex(): SearchEntry[]
}
```

### 3.3 Stage 3 の実装（`BundledModuleRegistry`）

```ts
/**
 * 全モジュール同梱・同期解決の registry。
 * Static / Offline 配布ではこれが正式な実装となる（全同梱は要件そのもの）。
 * Stage 3 では SaaS も同じ実装を使い、挙動を現行と完全に一致させる。
 */
export function createBundledModuleRegistry(modules: readonly ModuleData[]): ModuleRegistry
```

- 内部で `moduleId → ModuleData` の `Map` を 1 度だけ構築（現行の `find` より高速だが、**返す値は同一**）
- `getSearchIndex()` は `modules.flatMap(buildSearchIndex)` を memoize
- `getAllModules()` は受け取った配列をそのまま返す（順序不変）

デフォルトインスタンス:

```ts
// data/modules/index.ts は無変更（ALL_MODULES を export したまま）
export const moduleRegistry = createBundledModuleRegistry(ALL_MODULES)
```

**`moduleRegistry` の定義場所は `lib/moduleRegistry.ts` とし、`ALL_MODULES` を import する。** `data/modules/index.ts` は無変更に保つ（F-6 の整合テストが依存しているため）。

### 3.4 Stage 4 で加算する予定のメソッド（設計予告・Stage 3 では実装しない）

```ts
// Stage 4 で ModuleRegistry へ加算（既存メソッドは変更しない）
  getModuleAsync?(moduleId: string): Promise<ModuleData | undefined>
  getSearchManifest?(): SearchManifest
```

## 5. Stage 3 時点で現行挙動を完全維持する方法

### 5.1 維持の 6 条件

| # | 条件 | 実現方法 |
|---|---|---|
| M-1 | **同期性を保つ** | interface に `Promise` を導入しない |
| M-2 | **同一のオブジェクト参照を返す** | `getAllModules()` は `ALL_MODULES` をそのまま返す（複製・再構築しない） |
| M-3 | **順序を保つ** | `Map` は挿入順を保持。`getAllModules()` は元配列を返すため順序不変 |
| M-4 | **検索インデックスを同一にする** | `getSearchIndex()` は `ALL_MODULES.flatMap(buildSearchIndex)` と同一。memoize は結果を変えない |
| M-5 | **`ALL_MODULES` の export を維持する** | `data/modules/index.ts` 無変更。テスト 37 箇所が無改修 |
| M-6 | **`DashboardClient` を変更しない** | prop 名・型・値をすべて維持 |

### 5.2 機械的に検証する parity テスト（新規 `tests/moduleRegistry.parity.test.ts`）

```
□ moduleRegistry.getAllModules() が ALL_MODULES と同一件数
□ moduleRegistry.getAllModules() の各要素が ALL_MODULES の同 index と
  同一オブジェクト参照（=== 比較）
□ moduleRegistry.listModuleIds() が ALL_MODULES.map(m => m.moduleId) と deepEqual
□ 全 moduleId について getModule(id) === ALL_MODULES.find(m => m.moduleId === id)
□ 未登録 id で getModule() が undefined を返す
□ moduleRegistry.getSearchIndex() が ALL_MODULES.flatMap(buildSearchIndex) と
  deepEqual（entries 数・順序・全フィールド）
```

**`===` による参照同一性を検証する**ことで、「意図せず複製して別オブジェクトになった」ことを検知できる（React の再レンダリング挙動に影響するため重要）。

## 6. 将来 2 層 manifest へ差し替える接続点

### 6.1 単一の接続点: `getSearchIndex()`

```
Stage 3:
  getSearchIndex() → ALL_MODULES.flatMap(buildSearchIndex)     [全件から構築]

Stage 4:
  getSearchIndex() → buildIndexFromManifest(getSearchManifest())  [manifest から構築]
```

**`lib/search.ts` の `buildSearchIndex` は変更せず、manifest から `SearchEntry[]` を組み立てる関数を新設する。** これにより:

- 正規化ロジック（`normalizeText` / `SEPARATOR_PATTERN` / トークン分割順序）を再実装しない
- スコア関数（`scoreEntry` / `scoreEntryAND` 等）は無変更
- `DashboardClient` L166 の `useMemo` は `moduleRegistry.getSearchIndex()` を呼ぶだけになる

### 6.2 差し替えの段階

| 段階 | `getSearchIndex()` の実装 | S/O/A/P |
|---|---|---|
| Stage 3 | 全件 `buildSearchIndex` | 含む（現行どおり） |
| Stage 4-a | 全件 `buildSearchIndex`（本文除去版・`lib/search.ts` の 4 行削除） | **除外** |
| Stage 4-b | manifest から構築 | 除外 |

**Stage 4-a と 4-b を分ける。** 4-a は「本文除去」のみで、parity テスト（T-1）で検索結果同一性を検証できる。4-b は「2 層化」のみで、T-3（等価テスト）で検証できる。**2 つの変更を混ぜない。**

### 6.3 registry 実装の差し替え点

```
Static / Offline:  createBundledModuleRegistry(ALL_MODULES)      ← Stage 3 のまま
SaaS:              createManifestModuleRegistry(manifest, fetch) ← Stage 4-b で新設
```

選択は build 時（`EXPORT_STATIC` 相当の環境変数）で行う。**canonical JSON・型・Validator・UI は共通のまま。**

## 9. 各 Stage の commit 分割

| Stage | commit 数 | commit message 案 | 対象 |
|---|---|---|---|
| 1 | **1** | `chore(measure): add payload measurement script` | `scripts/measure-payload.ts` + `package.json` + PN8 |
| 2 | **1** | `fix(config): limit no-store to html and cache static assets` | `next.config.js` |
| 3 | **2** | ① `feat(registry): add module registry abstraction`（`lib/moduleRegistry.ts` + parity テスト）<br>② `refactor(app): route module access through registry`（`app/page.tsx`） | 上表 |

**Stage 3 を 2 commit に分ける理由**: ① は加算のみで既存挙動に一切触れない（rollback 不要な安全な追加）。② が実際の切り替え。**② のみを revert すれば挙動が戻る。**

各 commit の共通規則は既存工程を踏襲する（1 論点 = 1 commit / push は別途指示 / 許可済み差分 4 件を stage しない / `Co-Authored-By` 付与）。

## 10. rollback 方法

| Stage | rollback 手順 | 影響範囲 | 難易度 |
|---|---|---|---|
| 1 | 該当 commit を revert | 計測スクリプトが消えるだけ。production 挙動に影響なし | **最小** |
| 2 | `next.config.js` の revert | ヘッダが全経路 `no-store` へ戻る。ブラウザキャッシュは次回アクセスで無効化される | **小** |
| 3 | **② のみ revert**（① は残してよい） | `app/page.tsx` が `ALL_MODULES` 直接参照へ戻る。registry は未使用コードとして残る（無害） | **小** |

### rollback しやすさの設計上の担保

- **Stage 間に依存がない**: Stage 2 は Stage 1 に依存しない。Stage 3 も同様
- **Stage 3 の ① と ② が分離している**: 抽象の追加と、その利用開始が別 commit
- **`ALL_MODULES` を維持している**: どの段階でも「直接参照へ戻す」が常に可能
- **テストが無改修**: rollback 時にテストを戻す作業が発生しない
