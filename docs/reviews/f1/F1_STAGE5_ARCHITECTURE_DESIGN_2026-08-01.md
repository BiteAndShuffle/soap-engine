## 第 1 章 Stage 5 の目的

### 1.1 Stage 5 は何を解決する段階か

**Stage 5 は「配信境界を配布形態ごとに分離する」段階である。**

Stage 4 までで検索データの境界（本文を含まない構造化 manifest）は完成した。しかし**その manifest が production の配信量に一切影響していない**。Stage 5 が解決するのは、この「基盤はあるが接続されていない」状態である。

### 1.2 Stage 4 が解決したこと / 残したこと

| | 内容 | 状態 |
|---|---|---|
| **解決済み** | SOAP 本文に依存しない構造化検索データの生成（35 modules / 1,060 scenarios / 119 brands） | 完了 |
| **解決済み** | manifest の決定論性・stale 検出・ID 整合・カバレッジ・本文非混入の機械保証（T-1〜T-7） | 完了 |
| **解決済み** | `moduleLoader.getSearchIndex()` の manifest 由来化（差し替え接続点の確立） | 完了 |
| **解決済み** | 静的資産の長期キャッシュ（Stage 2）・配信量計測の常設化（Stage 1） | 完了 |
| **未解決** | **P-A: production の検索インデックスが `ALL_MODULES` 由来のまま** | Stage 5 |
| **未解決** | **P-B: 全モジュール JSON の初期クライアント配信** | Stage 5 |

未解決の 2 点は**欠陥ではなく、D-S4-1 (a) による意図的な範囲設定**である。理由は Stage 4 計画に記録されている。

> Client Component から `moduleLoader` を直接 import すると `ALL_MODULES` がクライアントバンドルへ引き込まれる可能性がある／現在の `allModules` prop と重複する危険がある／manifest を prop 追加しても `allModules` が残る段階では配信量削減にならない／production 接続は module payload 境界と一緒に後続 Stage で設計すべき

**3 番目の理由が Stage 5 の定義そのものである。** manifest だけを接続しても配信量は減らない。減らすには **module payload の境界**を同時に決める必要がある。

### 1.3 Stage 5 が解決する 2 つの問題

#### 問題 P-A: 検索インデックスの構築元

```
現在: DashboardClient が allModules（module payload 全件）から index を構築する
将来: 検索は Search Manifest のみから成立し、module payload を必要としない
```

Stage 4 の実測により、**manifest 由来の `SearchEntry[]` は canonical 由来と全 21 フィールドで完全一致する**ことが機械保証されている。したがって P-A は「技術的に可能か」ではなく「いつ切り替えるか」の問題である。

#### 問題 P-B: module payload の配信境界

```
現在: 全 35 モジュールの module payload が RSC ペイロードとして初期 HTML に埋め込まれる
将来: 形態に応じて「全同梱」または「必要時に取得」を選択できる
```

P-B は P-A と異なり、**技術判断だけでは決まらない**。形態ごとに正解が違う（第 4 章）。

### 1.4 Stage 5 のゴールと非ゴール

| | 内容 |
|---|---|
| **ゴール** | 配布形態ごとに配信境界を選択できる構造にすること |
| **ゴール** | Static / Offline の現行動作を一切変えないこと（全同梱は要件そのもの） |
| **非ゴール** | Static 版の全同梱をやめること（**変更しないことが正しい**） |
| **非ゴール** | 検索機能そのものの変更（Stage 4 で確定済み・本文検索の意図的喪失を含む） |
| **非ゴール** | canonical JSON の構造変更 |
| **非ゴール** | Enterprise 要件の実装 |

### 1.5 なぜ「今」実装しないのか

第 0.2 の優先順位に加え、次の構造的理由がある。

| # | 理由 |
|---|---|
| 1 | **現在の優先対象（Static / Offline）では全件配布が要件であり、配信境界を変える利益がない。** 遅延取得はネットワーク依存を生む方向に働くため、要件と逆行する |
| 2 | **P-B の正解は SaaS の商品設計に依存する。** 「未契約モジュールを送らない」という要件が、プラン・課金の単位が未確定のままでは設計できない（`F1_ARCHITECTURE_REVIEW` §8） |
| 3 | **接続点は既に確立されている。** `moduleLoader` interface と manifest があるため、着手時期を遅らせても再設計にはならない |

**payload サイズは保留理由に含めない。** サイズは第 9 章 B の着手トリガー（T-3 / T-4）としてのみ扱う。

### 1.6 Stage 4 と Stage 5 の位置づけの違い

| | 段階の性格 |
|---|---|
| **Stage 4** | **検索境界（Search Manifest）を作る段階。** 何を検索データとし、何を含めないかを確定した |
| **Stage 5** | **その境界を各配布形態でどう利用するかを決める段階。** |

**Stage 5 は新しい検索方式を設計する段階ではない。** 検索の挙動・スコアリング・対象フィールド・意図的な本文検索の喪失は Stage 4 で確定済みであり、Stage 5 はこれを変更しない。Stage 5 が扱うのは「確定した検索データを、どの形態で、どこから、どのタイミングで供給するか」である。

### 2.3 個別解決 8 箇所のアクセスパターン（本書で新たに実測）

8 箇所を実測したところ、**module 解決の直後に何をしているか**が 2 種類に分かれた。

| パターン | 箇所 | 直後の処理 | 必要な粒度 |
|---|---|---|---|
| **A. シナリオ 1 件を引く** | L466 / L884 / L1118 / L1268 / L1542（**5 箇所**） | `mod.scenarios.find(s => s.globalId === …)` または `s.id === …` | シナリオ単位で足りうる |
| **B. `ModuleData` 全体を保持する** | L363 / L1009 / L1047（**3 箇所**） | `return mod`（`ModuleData` として返す）／ `setActiveModuleData(mod)`（React state へ格納）／ ノード生成時に参照 | **モジュール全体が必要** |

**結論**: **module 単位 lazy load が現時点で最も自然な粒度であり、scenario 単位分割を採用するだけの実測上の必要性は確認されなかった。** パターン B の 3 箇所が `ModuleData` 全体を要求すること、パターン A の 5 箇所も module 単位ロードで当然に満たされることが根拠である。将来 canonical JSON の構造や `DashboardClient` のアクセスパターンが変われば再評価する。

### 3.2 各段の責務・粒度・同期性

| 段 | 責務 | 粒度 | 必要データ | 同期/非同期 |
|---|---|---|---|---|
| ① 検索 | クエリ → 候補 | 全モジュール横断 | `SearchEntry[]`（manifest 由来） | **同期**（メモリ内スコアリング） |
| ② Manifest | 検索データの供給 | module 35 ＋ scenario 1,060 | manifest のみ | 形態依存（同梱=同期 / 取得=非同期） |
| ③ Module Load | moduleId → ModuleData | **モジュール単位** | module payload | 形態依存 |
| ④ Scenario 解決 | id → Scenario | シナリオ単位 | ③の結果内 | **同期**（メモリ内 `find`） |
| ⑤ SOAP 生成 | Scenario → S/O/A/P | ノード単位 | ③の結果 | **同期** |

**非同期になりうるのは ② と ③ のみである** — ただしこれは **Client-side SOAP 生成を維持する場合に限る**。①④⑤は取得済みデータ上の純粋な計算であるため、現在の想定では形態によらず同期で成立する。

**将来 SOAP 生成（⑤）を Server 側へ移す場合、⑤もネットワーク境界を持つため本表を再評価する必要がある**（第 5 章・第 6 章）。

## 第 4 章 配布形態別アーキテクチャ

### 4.0 本章の前提

- **4 形態を同時に実装することを目的としない。**
- **共通化は、現在必要な範囲を超えて行わない。**
- Static / Offline では**全同梱が要件であり、変更しないことが正しい**
- SaaS は設計のみ。Enterprise は前提条件の確認のみ

### 4.1 4 形態の位置づけと着手区分

| 形態 | 事業上の位置づけ | **着手区分** | 本書での扱い |

| **Static 版** | 現在の優先対象 | **現在必要** | 現行構造の記述。**変更しないことの確認**が主目的 |
| **Offline 版（店舗向け）** | 現在の優先対象 | **現在必要** | Static を基礎とし、**運用要件の差分**を整理（§4.5） |
| **SaaS 版** | 将来の一般提供における主軸候補 | **今は設計のみ**（将来必要） | 構造の整理のみ |
| **Enterprise 版** | SaaS 設計を基礎にした将来拡張 | **今回は対象外** | 前提条件の確認のみ |

#### Stage 5 の 3 対象（S-1 / S-2 / S-3）× 形態の着手区分

| | S-1 Manifest の production 利用 | S-2 module payload 取得境界 | S-3 Express 候補の供給境界 |
|---|---|---|---|
| **Static** | **現在は実装不要。将来の任意最適化候補** | **現在対象外。**全同梱を維持 | **現在対象外。**現行どおり module payload から構築 |

**S-2 / S-3 は SaaS 固有であるが、S-1 は SaaS 固有ではない。** Static / Offline でも、次の改善余地を持つ**任意最適化候補**として将来利用しうる。

| 改善余地 | 内容 |
|---|---|
| 初期パース量 | 検索のために全 module payload をパースする必要がなくなる |

| scenario 取得 | Static と同一 |
| SOAP 生成 | Client-side |
| Cache | 不要。**ネットワークが存在しない前提のため、キャッシュという概念自体が成立しない** |
| 配信境界 | 境界なし |

**全同梱は Offline 版の要件そのものである。**

### 4.5 Static 版と Offline 版の差分

| 軸 | **Static 版** | **Offline 版（店舗）** | 差の性質 |
|---|---|---|---|
| **更新方法** | 配布物の差し替え。配布先が web ホスティングであれば再デプロイで反映しうる | **端末ごとの再配布**。更新が届く保証がなく、**バージョン混在が起こりうる** | **大きく異なる** |
| **ネットワーク依存** | 配布形態により変動 | **ゼロ**（初回配布後）。可用性要件そのもの | 異なる |
| **認証** | `middleware.ts` が無効のため Basic 認証が効かない | **端末が物理的に管理された環境**にあることが前提 | 異なる |
| **ライセンス** | 配布物に制限がない | **端末内に全データが存在するため、ライセンス管理が課題** | **Offline 固有** |
| **Cache** | ホスティング側の設定に依存 | **概念として成立しない** | 異なる |
| **配布物の改変耐性** | ホスティング上のファイルは通常ユーザが改変できない | **端末上の配布物へ書き込み権限を持つ主体がいる場合、build 成果物中にシリアライズされた薬学データを改変できる可能性がある。** 現在、配布物の**署名・ハッシュ検証・改変検知・信頼済み更新経路は設計されていない** | **Offline 固有かつ重大** |

#### 差分から導かれる示唆

| # | 示唆 |
|---|---|
| 1 | **Offline 版は Static 版にない課題を持つ。** これらは F-1 のスコープ外であり、**3 件の別課題として分離する**（§10.3）— ①配布物の完全性・改変検知（セキュリティ／医療内容の完全性）②更新・バージョン統制（運用）③ライセンス管理（商用ライセンス） |
| 2 | **Offline 版はバージョン混在を前提とすべき。** `BUILD_SHA` 表示（実装済み）のような自己識別手段が運用上重要になる |
| 3 | Static / Offline とも**配信境界を持たない**ため、Stage 5 の S-2 / S-3 は対象外である |

### 4.6 SaaS 版

### 5.2 現在のアプリ実装における、ユーザー入力の外部送信・永続化経路

本書で実測した結果、**現在の Repository 実装には、ユーザー入力内容をアプリ管理下のサーバまたは永続ストレージへ送信・保存する経路がない。**

| 検査対象（`app/` `lib/`） | 実測 |
|---|---|
| API route（`app/api` / `route.ts`） | 0 件 |
| `fetch(` / `XMLHttpRequest` / `navigator.sendBeacon` | 0 件 |
| `localStorage` / `sessionStorage` | 0 件（未使用の legacy `LockGate.tsx` を除く） |
| SOAP の出力経路 | `navigator.clipboard.writeText`（クリップボードのみ） |

#### 入力経路の区分

| 経路 | 状態 | 送信の有無 |
|---|---|---|
| `SoapEditor.tsx` の S/O/A/P textbox | **UI 接続済み** | 送信なし。`onChange` は親 state のみ更新 |
| `NlpInputPanel.tsx` の自由入力 | **未接続の将来候補。** JSX には存在する（L30 import / L1931 描画）が、`uiMode === 'nlp'` への遷移が `showNlpButton = false` により塞がれており**実行時に到達しない**（コード注記 L1668・L276 と一致） | 仮に到達しても `createSoapFromInput` はローカル関数であり送信は発生しない |

#### 本実測の射程外

**本実測が確定したのは「現在の Repository 実装内」に限られる。** 次はいずれも射程外であり、本書では評価していない。

- ブラウザ拡張機能
- OS のクリップボード履歴・同期機能
- hosting / reverse proxy / CDN のアクセスログ
- 将来追加されうる analytics / monitoring SDK
- クリップボードからの貼付先（電子薬歴システム等）
- 端末・ブラウザ自体の挙動（同期・バックアップ・入力予測等）

**したがって「システム全体として絶対に egress がない」とは主張しない。** 本書が扱うのは、アプリ実装として送信・永続化の経路を持たないという構造的性質である。

**この性質は Stage 5 の設計判断における重要な制約候補である。** ただし本書はこれを不変条件として固定せず、比較材料として提示する（**D-S5-8**）。

### 5.3 将来の境界（形態別）

| 形態 | Server 側 | Client 側 | 境界を越えるもの |
|---|---|---|---|
| **Static** | **存在しない**（build 時のみ） | すべて | — |
| **Offline** | **存在しない** | すべて | — |
| **SaaS（基準案）** | モジュール解決・Validator ＋ **manifest / module payload の供給・認可** | 検索・SOAP 生成・合成・persona | manifest ／ 契約範囲の module payload |
| **SaaS（比較案）** | 上記 ＋ **SOAP 生成** | UI・編集のみ | 上記 ＋ 選択情報 ／ 生成結果 ／ 場合により入力内容 |

**Static / Offline に Server は存在しない。** したがって Server 側へ責務を移す設計は、**形態間の機能互換を壊さない範囲でのみ**成立する（I-8）。

### 5.4 基準案 — Client-side SOAP 生成の維持

**本書は Client-side SOAP 生成の維持を基準案とする。**

| 観点 | 評価 |
|---|---|
| **形態互換** | **4 形態すべてで同一実装が成立する** |
| **入力データの送信・永続化** | **§5.2 の性質を維持できる** |
| **Offline 成立性** | **完全に成立** |
| **実装変更量** | **ゼロ**（現行のまま） |
| **秘匿性（医療内容）** | module payload がクライアントへ届くため、**SOAP 本文がクライアント側に存在する** |
| **監査ログ** | **SOAP 生成内容・scenario 選択・編集内容に関するアプリケーションレベルの監査ログを、サーバ側で取得できない**（記録点が存在しないため）。※ hosting / reverse proxy の一般的なアクセスログやエラーログの有無は本書の射程外 |
| **未契約モジュールの非配信** | **S-2 により達成可能** |

#### 秘匿性に関する 2 点（混同しない）

| # | 内容 |
|---|---|
| 1 | **未契約モジュールをクライアントへ送らないことは S-2 により実現可能である。** SOAP 生成の場所とは独立する |
| 2 | **一方、契約範囲内でクライアントへ配信した module 内容は、クライアントから秘匿できない。** S/O/A/P 本文を含む module payload が端末上に存在するため |

### 5.5 比較案 — Server-side SOAP 生成

| 観点 | Client-side（基準案） | Server-side（比較案） |
|---|---|---|
| **医療内容の秘匿性** | module payload がクライアントへ届く。**本文自体は秘匿できない** | **本文をサーバに留められる** |
| **監査要件** | アプリケーションレベルの監査ログの記録点がない | **記録点を持てる。** Enterprise の監査要件を満たしうる |
| **ログ** | 上記のとおり | 取得できる。**ただし何を記録してよいかの判断が必須** |
| **患者情報の送信・保存** | **§5.2 のとおり送信も保存もしない** | **設計次第で送信・保存が発生する** |
| **Offline 成立性** | **完全に成立** | **成立しない。** Client 側実装を残す必要があり二重実装になる |

#### 送信しうる情報の区分

| 区分 | 内容 |
|---|---|
| **A** | `moduleId` / `scenarioId` / `globalId` 等の**選択情報のみ** |
| **B** | 選択情報 ＋ **構造化された患者状態** |
| **C** | **S/O/A/P の自由入力・編集内容** |
| **D** | **生成結果または監査記録の保存** |

**区分 A であっても、利用履歴や診療上の関心を推測しうる情報になる可能性がある。** 「選択情報だから患者情報ではない」とは扱わない。

#### 決定順序（API 形式より先に決める）

**送信・処理・保存・ログを同一の判断として扱わない。**

1. **何を送るか**（A / B / C の区分）
2. **何を処理するか**（送ったもののうち、サーバで計算に使う範囲）
3. **何を保存するか**（D。処理しても保存しない選択がありうる）
4. **何をログへ残すか**（保存とログは別。ログの粒度・内容も別判断）
5. **どの期間保持するか**（保存とログそれぞれについて）

#### 比較から導かれる論点

| # | 論点 |
|---|---|
| 1 | **Server-side 生成は「秘匿性」と「監査」を得る代わりに、§5.2 の性質と「単一実装」を失う。** 交換関係にある |
| 2 | **Offline 成立性（I-8）を維持する限り、Client 側 SOAP 生成の実装は削除できない。** したがって Server-side は「置き換え」ではなく「**追加**」になり、二重実装の維持コストが発生する |
| 3 | 区分 A であっても、**サーバ側に「どのモジュールのどのシナリオが選ばれたか」というログが残る**。これ自体が診療情報の断片になりうる |
| 4 | Enterprise の監査要件が Server-side を要求する場合、**SaaS 設計の時点でその可能性を排除しない構造にしておく**必要がある |

### 5.6 比較結論

| # | 結論 |
|---|---|
| 1 | **Client-side SOAP 生成の維持を基準案とする** |
| 2 | **Server-side SOAP 生成は Stage 5 の対象に含めない。** S-1/S-2/S-3 の解決に必須ではなく、独立した設計判断である |
| 3 | ただし **Server-side を将来の選択肢として排除しない**（**D-S5-5**） |
| 4 | Server-side を検討する場合、**最初に決めるべきは「何をサーバへ送るか」**であり、API の形ではない |
| 5 | **§5.2 の性質を変更する場合は明示的な判断として扱う。** 副次的・暗黙的に失わせない |

### 5.7 本章で決めなかったこと

| ID | 論点 |
|---|---|
| **D-S5-8** | §5.2 の性質を不変条件へ昇格させるか |
| **D-S5-5** | Server-side SOAP 生成を将来採用するか（§4.9 と同一論点） |
| **D-S5-9** | 認可判定を Server / Client のどちらで行うか |

### 6.2 責務候補

|---|---|---|---|---|
| **R-α** | **検索データの供給** | （契約範囲の識別情報） | Search Manifest 相当の構造化検索データ | SaaS |
| **R-β** | **module payload の供給** | `moduleId` | `ModuleData` 1 件 | SaaS |

### 6.3 R-δ の分解 — 3 責務と Entitlement の 3 層

| 責務 | 問い | 確定要否 |
|---|---|---|
| **Authentication** | **誰であるか** | 着手時まで保留可（具体方式は N-2） |
| **Entitlement resolution** | **何を利用できるか** | **API 設計に先行して確定が必要** |
| **Authorization** | **今回の要求を許可するか** | Entitlement モデル確定後 |

Entitlement resolution はさらに **3 層に分離する。**

| 層 | 内容 | 判定単位の候補 |
|---|---|---|
| **A. Content entitlement** | **何のコンテンツへアクセスできるか** | module 単位 ／ 診療領域単位 ／ 薬効分類単位 ／ module 集合単位 ／ 店舗・法人単位 |
| **B. Capability entitlement** | **どの機能を利用できるか** | 1 剤 SOAP 生成 ／ 多剤合成 ／ ペルソナ変換 ／ 在庫管理 ／ 分析機能 |
| **C. Commercial policy** | **A と B を、どの利用者へ・どの時期に・どの条件で開放するか** | 契約プラン ／ Free・Paid ／ キャンペーン期間 ／ 新規・既存利用者 ／ 月間利用回数 ／ 提供地域 ／ 提供開始時期 |

**C は A・B と分離する。** 「特定領域を無料にする」という条件をコードへ直接固定せず、**現在の Commercial policy が、どの Content entitlement とどの Capability entitlement を Free 利用者へ付与するかを決める構造**とする。これにより無料範囲を設定変更で再設計できる。

**具体的な識別子・設定形式・schema・領域構成は本書で確定しない。**

#### 判定単位が決めるもの

| 決まるもの | どの層に依存するか |
|---|---|
| Search Manifest の返却範囲 | **A** |
| Express 候補の返却範囲 | **A** |
| `ModuleData` の取得可否 | **A** |
| 多剤合成・ペルソナ変換等の実行可否 | **B** |
| cache 共有境界 | **A**（module 集合が異なるか）＋ **C**（割り当てのみの変更か） |

### 6.4 責務間の関係

```
   R-δ 契約・権限の判定（Authentication / Entitlement resolution / Authorization）
        │ 利用可能なコンテンツ集合・機能集合
        ├──────────────┬──────────────┐
        ▼              ▼              ▼
   R-α 検索データ   R-γ Express    R-β module payload
        │              │              │
        │              │              │  ★ R-α/R-γ は起動時
        │              │              │  ★ R-β は選択時（遅延）
        ▼              ▼              ▼
   ────────────── Client 側 ──────────────
        検索 → Express → module 解決 → SOAP 生成（基準案）
                                    （比較案では SOAP 生成が R-ε として Server 側へ移る）
```

| # | 関係 |
|---|---|
| 1 | **R-δ がすべての前提**である。**課金・プランの単位と entitlement の判定単位の確定が API 設計の先行条件**（第 9 章 B へ接続） |
| 2 | **R-α / R-γ は起動時に 1 回**、**R-β は選択時に都度**という取得タイミングの差がある。キャッシュ戦略が異なる |
| 3 | **R-γ は §3.3 の案により R-α へ統合されうる**（**D-S5-10**） |
| 4 | **R-ε は §5.6-2 により Stage 5 の対象外** |

### 6.5 Static / Offline での代替経路（API を持たない）

| 責務 | Static / Offline での代替 |
|---|---|
| R-α 検索データの供給 | 同梱データから同期的に構築（現行 `buildSearchIndex` ／ 将来 S-1 を任意採用すれば同梱 manifest から） |
| R-β module payload の供給 | **全同梱**から同期解決（現行 `moduleLoader.getModule`） |

| R-ε SOAP 生成 | **Client-side** |

**責務は共通、実装は形態別**という §4.8 原則 2 の具体例がここに現れる。

### 6.6 利用実績に基づく無料範囲の再設計

SaaS 提供後は、**個人を特定する患者情報を収集しなくても**、商品設計に必要な利用傾向を取得できる可能性がある。

**分析候補**: 検索された診療領域 ／ 選択された module ／ 1 剤 SOAP 生成の利用回数 ／ 多剤合成の開始率・完了率 ／ ペルソナ利用率 ／ paywall が表示された機能 ／ Free から有料への移行契機 ／ 継続利用される領域 ／ 検索したが候補を選択しなかった割合

これにより将来、**無料領域を維持する ／ 追加する ／ 入口領域へ絞る ／ 領域は無料のまま多剤合成のみ有料にする ／ 期間限定で無料開放する**といった判断が可能になる構造とする。

**本書では分析イベント名・分析サービス・保存期間・集計 schema を確定しない。**

### 6.7 利用分析と医療情報の分離

| 収集候補 | 原則として収集しない候補 |
|---|---|
| domain / category ／ moduleId ／ 利用機能種別 ／ entitlement 状態 ／ 成功・中断 ／ paywall 表示 ／ 集計可能な利用時刻 ／ plan category | 患者氏名 ／ 患者 ID ／ 自由入力した S/O/A/P ／ 生成済み SOAP 本文 ／ 処方内容そのもの ／ 個別患者を推測できる詳細な薬剤組み合わせ ／ 構造化された患者状態 |

**特に複数 module の組み合わせは、患者像や疾患を推測できる可能性があるため、分析上本当に必要かを個別に判断する。**

利用分析を導入すると、**§5.2 で実測した性質が部分的に変わる。** したがって分析導入は暗黙に行わず、**何を送るか ／ 何を保存するか ／ 集計粒度 ／ 保持期間 ／ 個人や患者との紐付け可否 ／ opt-out の要否**を明示的に判断する**別工程**とする（**D-S5-18**）。

**利用分析は本書において必須要件ではない。** 実施するか否かを含めて Owner 判断とする。

| ID | 論点 |

| **D-S5-11** | R-β の返却粒度（`ModuleData` 全体か部分か） |

## 第 9 章 Owner Decision の評価

### 9.0 本章が前提とする事業上の方向性

**価格・プラン名・無料領域はいずれも未確定であり、本書は確定事項として扱わない。** 前提とするのは次の方向性のみである。

- 初期は普及を優先する
- **1 剤 SOAP 生成は広く無料とする候補**
- **多剤合成は有料候補**
- **ペルソナは上位有料候補**
- 在庫・分析は将来の高機能候補
- SaaS 利用実績を基に、将来 Free 対象領域を変更する可能性がある
- 風邪・点眼等を入口となる無料領域にする案は**候補であり未確定**
- Entitlement と Commercial policy を分離し、無料範囲を設定変更できる構造を残す

### 9.1 評価 A — Content Delivery Boundary トラックの保留判断は妥当か

**結論: 現時点で Content Delivery Boundary トラックの実装を保留する判断は妥当である。**

**Capability Control、Commercial Policy、Usage Analytics については、それぞれの商品・SaaS 要件が具体化した時点で独立に判断する。** 本評価は Stage 5 全体または SaaS 関連作業のすべてを保留するものではない。

| # | 根拠 | 裏付け |
|---|---|---|
| **EV-1** | **現在の優先対象（Static / Offline）では配信境界を変える利益がない。** 全同梱が要件であり、遅延取得はネットワーク依存を生む方向に働く | §1.5 ／ §4.1 |
| **EV-2** | **Stage 5 の 3 対象のうち S-2 / S-3 は SaaS 固有**であり、現在の優先対象では対象外 | §4.1 |
| **EV-3** | **接続点は既に確立されている。** `ModuleLoader` interface（Stage 3）と Search Manifest（Stage 4）があり、着手を遅らせても再設計にはならない | §2.6 C-3 |
| **EV-4** | **着手前に決着が必要な条件が未確定**である。特に K-7（Express 供給源）と entitlement モデル | §8.3 |
| **EV-5** | **初期の商品方針では、Content Delivery Boundary が SaaS 開始の必須前提にならない可能性が高い** | §9.2 |

### 9.2 実装トラックの再整理

**F-1 以降のロードマップを、単純な直列 Stage として扱わない。** 次の 4 つは**独立して先行・並行しうる実装トラック**である。

| トラック | 内容 | S-1/S-2/S-3 との対応 |
|---|---|---|
| **A. Content Delivery Boundary** | Search Manifest の供給 ／ `ModuleData` の供給 ／ Express 候補の供給 ／ **Content entitlement による配信範囲** | **S-1・S-2・S-3 が属する** |
| **B. Capability Control** | 1 剤 SOAP 生成 ／ 多剤合成 ／ ペルソナ変換 ／ 在庫・分析等の将来機能の実行可否 | — |
| **C. Commercial Policy** | Free / Paid ／ 無料領域 ／ キャンペーン ／ 回数制限 ／ 新規・既存利用者への割り当て ／ 経過措置 | — |
| **D. Usage Analytics** | 商品判断用の利用傾向 ／ Free 範囲の再設計に必要な集計 | — |

#### 初期 SaaS における必要性

| トラック | 初期 SaaS での必要性 | 根拠 |
|---|---|---|
| **B. Capability Control** | **必要になる可能性が高い** | 初期の課金軸が Capability（多剤合成 = 有料候補／ペルソナ = 上位有料候補） |
| **C. Commercial Policy** | **必要になる可能性が高い** | Free / Paid の割り当てが発生する |
| **A. Content Delivery Boundary** | **必須前提とは限らない** | 全利用者へ同じ module 集合を提供するなら配信範囲を絞る必要がない |
| **D. Usage Analytics** | **必要に応じて。必須要件ではない** | Free 範囲の再設計を行う場合に必要 |

> **初期 SaaS では、B と C が A より先に必要になる可能性がある。**

#### S-1 の位置づけ

**S-1（Search Manifest の production 利用）はトラック A に属するが、A の他要素とは異なり独立した着手トリガーを持つ。**

| S 対象 | 主たるトリガー | 独立トリガー |
|---|---|---|
| **S-1** | Content entitlement の導入 | **あり** — 初期パース量／メモリ使用量／起動時の全件展開／検索データと `ModuleData` の責務分離という**性能・構造上の任意最適化**として、Content entitlement がなくても価値を持つ |
| **S-2** | Content entitlement の導入 | なし（配信境界と強く結合） |
| **S-3** | Content entitlement の導入 ／ P-B の解決 | なし（同上） |

**「トラック A は Content entitlement 導入時にのみ着手する」とはしない。** S-1 は性能上の必要が観測された時点でも着手しうる。**Static / Offline においても、全同梱を維持したまま任意最適化候補として残る。**

#### 段階番号の扱い

**本書では段階番号の付け替えを行わない。** 直列 Stage を維持するか独立トラックへ再編するかは **D-S5-20** として Owner 判断へ送る。
