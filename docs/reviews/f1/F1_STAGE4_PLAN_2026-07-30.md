## 3. Manifest schema

### 3.1 2 層構造

```ts
interface SearchManifest {
  manifestVersion: string   // 生成器バージョン
  sourceHash: string        // 生成元 canonical 構造化データの内容ハッシュ（D-S4-9）
  moduleCount: number       // 整合検証用
  scenarioCount: number     // 整合検証用
  modules: ManifestModule[]     // 35 件（モジュール単位・重複排除）
  scenarios: ManifestScenario[] // 1,060 件（シナリオ単位）
}
```

#### `sourceHash` の仕様（D-S4-9）

**`generatedFrom`（生成元 commit SHA）は廃止する。** commit SHA は canonical JSON が不変でも commit のたびに変化するため、T-3 の「バイト一致」が構造的に成立しない。代わりに**生成元データの内容ハッシュ**を保持する。

| 項目 | 仕様 |
|---|---|
| アルゴリズム | **SHA-256** |
| 表現 | **小文字 hex 文字列** |
| エンコード | **UTF-8** |
| **含めないもの** | Git HEAD ／ 生成日時 ／ 絶対パス ／ その他の環境依存値 |
| ハッシュ対象 | **Search Manifest 生成に実際に使用する入力フィールドだけを抽出した正規化済みデータ**。SOAP 本文など manifest 生成に使用しないフィールドは `sourceHash` の対象にも含めない |
| 自己参照 | **`sourceHash` 自身はハッシュ対象に含めない** |

**正規化条件**:

- **module は `ALL_MODULES` 登録順を保持する**（D-S4-10。`moduleId` で並べ替えない）
- scenario は各モジュール内の出現順を保持する（一意キーは `moduleId` + `globalId`）
- 配列は、**意味上順序を保持するものは原順序を維持**し、**集合として扱うものだけ安定ソート**
- object key 順を安定化
- `undefined` や環境依存表現を含めない

**Manifest は検索実行時に利用する順序を保持する。** 検索結果の順序も manifest の意味の一部であり、`buildIndexFromManifest()` が返す `SearchEntry[]` の並びが `buildSearchIndex()` を `ALL_MODULES` へ適用した結果と一致することが T-3 の deepEqual の前提となる。

**`sourceHash` は manifest 全体（`sourceHash` 自身を除く）の決定論的直列化に対して計算する。** module 配列の順序も `sourceHash` の対象に含める。ハッシュ対象が manifest そのものであるため、「**manifest が変化した時だけ `sourceHash` も変化する**」という性質が定義上保証される。

**T-3 では `sourceHash` を比較対象から除外する例外を設けない。** canonical から再構築した完全な manifest と commit 済み `data/search-manifest.json` のバイト一致を維持する。

### 3.3 `ManifestModule`（モジュール単位・35 件）

```ts
interface ManifestModule {
  moduleId: string
  categoryPath: string[]              // 薬効領域 + 剤形（末端）
  classKey?: string                   // 薬効分類（構造化キー）
  nodeKey?: string                    // 剤形（{classKey}_{route}）
  clinicalDomain?: string             // 薬効領域（構造化キー）
  displayTitle?: string
  displaySubtitle?: string
  brandNames: string[]                // 先発品名
  nameAliases: string[]
  drugClass: string[]
  drugSpecificTags: string[]
  search: {
    primaryDisplayName?: string       // 一般名
    exactAliases: string[]            // 読み仮名（完全一致）
    nameAliases: string[]
    keywords: string[]
    formulationSearchTokens: string[] // 剤形トークン
    priority: number
    matchPolicy: Record<string, unknown>
  }
  reservedHandlingTags?: string[]     // dosage variant（D-S4-4: 構造化値が存在する場合のみ）
  brandCatalog: Record<string, {
    // キー自体（brand 名）を検索対象として保持する（D-S4-3）
    displayName?: string              // 存在する場合のみ。generator による補完・創作は禁止
    displayGenericName?: string       // 後発品名 / 一般名
    genericKey?: string
    aliases: string[]
    indicationLabel?: string
    handlingTags?: string[]           // brandCatalogIndicationLabelMap の再構築用（D-S4-11）
  }>
}
```

`brandCatalog` から取るのは上記 6 フィールドのみ。

#### `handlingTags` を保持する理由（D-S4-11）

`lib/search.ts` L219-229 が `SearchEntry.brandCatalogIndicationLabelMap` を導出する際、`brandCatalog[brand].handlingTags` を参照している。

```ts
if (crossModuleIndicationLabel) {
  const cat0 = moduleData.categoryPath?.[0] ?? ''
  for (const [brand, entry] of Object.entries(brandCatalog)) {
    const tags = entry.handlingTags ?? []          // ← ここで参照
    const hasHeartFailure = tags.includes('heart_failure_supported')
    const hasCkd = tags.includes('ckd_supported')
    brandCatalogIndicationLabelMap[brand] =
      hasHeartFailure && hasCkd ? '心・腎' : hasCkd ? '腎' : hasHeartFailure ? '心' : cat0
  }
}
```

したがって `handlingTags` は**最終的な `SearchEntry` の内容へ影響する検索関連メタデータ**であり、「canonical 由来の `SearchEntry` = manifest 由来の `SearchEntry`」を決定論的に再現するために必要である。

**保持条件**:

| 条件 | 内容 |
|---|---|
| そのまま保持 | canonical の `brandCatalog` entry に存在する `handlingTags` をそのまま保持する |
| 推測・補完の禁止 | generator による推測・補完・名称変換を行わない |
| 縮約の禁止 | 現在参照されている 2 値（`heart_failure_supported` / `ckd_supported`）だけへ縮約せず、**配列全体を保持**する |
| 順序 | 配列の**原順序を維持**する |
| ハッシュ対象 | `sourceHash` の対象へ含める |
| 用途の限定 | **`SearchEntry` 再構築専用**とし、SOAP 生成やブランド制御の新たな入力には使用しない |
| 本文非混入 | **SOAP 本文ではないため T-6 の本文非混入原則には抵触しない** |

**D-S4-3 の適用**: `brandCatalog` の**キー（brand 名）が検索対象の実体**であり、`displayName` は補助である。`dm_insulin_mixed_rapid_long` の「ライゾデグ」のように `displayName` を持たない brand はキーのみを保持し、**generator は欠落を補完しない**（現行 `buildSearchIndex` も `displayName` を optional 扱いするため検索挙動は変わらない）。

**D-S4-2 の適用**: `manufacturer` フィールドは**スキーマに定義しない**。将来 canonical へ導入された時点で別途設計する。

### 3.4 `ManifestScenario`（シナリオ単位・1,060 件）

  globalId: string              // SearchEntry.templateId
  id: string                    // Express 候補の解決 / groupLabel 導出
  title: string                 // label / shortLabel・検索対象
  scenarioGroup: string         // groupLabel 導出・検索対象

  // ── 分類メタデータ（D-S4-8）─────────────────────────────

#### 分類メタデータ 4 項目の位置づけ（D-S4-8・重要）

| 項目 | 実在性 | 用途 |
|---|---|---|

## 6. 生成方法

| 項目 | 方針 |
|---|---|
| **source of truth** | canonical JSON（`data/modules/*.json`）。bridge → JSON の決定論性は PN2 §85 と `audit-alias-bridge-chain.ts` が既に統治済み |
| **deterministic 生成** | フィールド allowlist（§3.3 / §3.4）のみ抽出。順序は `ALL_MODULES` の登録順に固定、`scenarios` は JSON 内の出現順。**同一 commit から生成した manifest はバイト単位で一致する** |
| **手編集禁止** | 生成物の冒頭に「自動生成・手編集禁止」を明記。**T-3（等価テスト）が手編集を検出する**（canonical JSON から再生成した内容と一致しなければ FAIL） |
| **build 前生成の要否** | **不要**。生成物を commit するため build 時生成は行わない。理由: build 経路に生成ステップを足すと Static export・Vercel 双方で失敗点が増える。かつ生成物が git 管理下にあれば差分レビューが可能になる |
| **stale manifest 検出** | **T-3 が担う**。`npm test` 実行時に「canonical JSON から生成した manifest」と「commit 済み manifest」を比較し、不一致なら FAIL。`moduleCount` / `scenarioCount` の突合も行う |
| **差分の安定性** | オブジェクトキー順を固定（型定義の宣言順で明示的に構築）。`JSON.stringify` の第 3 引数でインデント 2 に固定。**モジュール追加時は該当モジュールのブロックのみが差分になる** |
