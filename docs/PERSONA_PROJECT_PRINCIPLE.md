## 1. 最終到達形

### 1.1 到達形の定義

〔Owner〕Persona Project の到達形は次のとおりである。

```
確定した base 指導文（全 module）
        ↓  上位 AI による生成
人格別の文章（約5人格分）
        ↓  人間によるレビュー
医療的意味が一切変わっていないことを確認できた文章のみ
        ↓  収録
固定データとしてアプリへ収録
```

要点は 3 つある。

| # | 要点 |
|---|---|
| 1 | **生成は事前（オフライン）で行う。** アプリ実行時に文章を作らない |
| 2 | **品質保証は人間のレビューによる。** 変換ルールの正しさではなく、生成物そのものを人が確認する |
| 3 | **Persona Project の最終完成形では、人格別文章の生成を runtime で行わず、アプリが主要な成果物として扱うのはレビュー済み固定文章とする** |

要点3について補足する。**現行の機械変換実装（`lib/applyPersona.ts` / `PERSONA_PROFILES` 等）は runtime で稼働している**〔実測〕。**これを将来も併存させるかは §7.4 の判断時点まで保留する。** 現行実装が存在しないかのように読まないこと。

### 1.2 なぜリアルタイム変換方式ではないのか

医療文書という対象の性質から導かれる。

| 観点 | リアルタイム変換方式 | 固定文章方式 |
|---|---|---|
| 出力の事前確認 | できない。ルールの組み合わせにより未知の文が出る | **できる。収録前にすべて人が読む** |
| 品質の保証単位 | 変換ルール（間接的） | **出力文そのもの（直接的）** |
| 医療的意味の不変性 | ルールが正しければ保たれる、という前提に依存 | **1 文ずつ確認された事実として保証される** |
| 未知の入力への挙動 | ルールが想定しない文で破綻しうる | 破綻しない（固定文しか出ない） |
| 柔軟性 | 高い | 低い（生成済みの人格・module に限定される） |

医療指導記録では、**出力を事前に全数確認できること**が柔軟性より優先される。この判断が方式選択の根拠である。

> **この表は最終完成形どうしの方式比較であり、現行 Repository の状態を記述したものではない。** 現行実装の位置づけは §2.4 を参照。

なお、この判断は「リアルタイム変換が技術的に不可能だから」ではない。実際に変換系は動作している〔実測〕。判断の根拠は §2.2 に記す実物評価の結果である。

### 1.3 「約5人格」という規模の位置づけ

〔Owner〕約5人格は**現時点の想定であり、確定値ではない**。

| 項目 | 状態 |
|---|---|
| 人格数 | 約5（想定） |
| 各人格の具体的な性格・文体 | **未定**。第3段階で決定 |
| 人格の切り分け軸 | **未定**。現行 4 軸を使うか否かも含めて第3段階で判断 |

人格数を先に確定しない理由は §2.6 PP-L-1 と同じである。実物を生成して評価する前に人格の切り分けを固定すると、**評価によって初めて分かる「人格として意味のある差」ではなく、設計時に想像した差**を仕様として固定してしまう。

### 1.4 この方式が現在へ課す制約

固定文章方式を採ることで、**現在の作業に 2 つの制約が発生する**。

| # | 制約 | 帰結 |
|---|---|---|
| **PP-C-1** | **生成の元になる base 指導文が確定していなければ生成できない** | base の完成（第1段階）が前提条件になる（§3.2） |
| **PP-C-2** | **base が変わると、その module の全人格分が無効化する** | 5 人格なら再生成・再レビューが 5 倍発生する。base の凍結が生成開始の条件になる（§3.4.1） |

リアルタイム変換方式であれば PP-C-2 は発生しない（base が変われば変換結果も自動的に追随する）。**PP-C-2 は固定文章方式を選んだことの直接の帰結であり、開発順序を規定する。**

さらに、この方式は**構造（器）についての制約を課さない**。人格別固定文章がどのような構造で収録されるかは未定だが、**それを受ける枠を canonical に通しておくこと自体は、構造が未定でも実行できる**。この非対称性が、現在 `module.persona` を保持している理由である（§4）。

## 2. 機械変換方式を最終形としなかった経緯

### 2.0 本章の性格

本章は過去の研究を否定するために書かれていない。

過去の研究によって「**AI が変換できること**」と「**Owner が求める人格品質へ到達すること**」が別問題であると判明した。この知見は、実際に変換系を作って大量の文章を評価しなければ得られなかった。したがって過去の実装は、失敗して無価値になったものではなく、**「最終仕様を確定するには実物評価が必要である」という知見を得るための検証資産**である。

本章はこの位置づけを前提とする。

### 2.1 何を研究したか

〔Owner〕開発初期に、ルールベース・機械変換による persona 生成を相当の時間をかけて研究した。

〔実測〕その成果は現在も Repository に存在し、稼働している。

| 資産 | 実体 | 備考 |
|---|---|---|
| 変換エンジン | `lib/applyPersona.ts` | — |
| 適用可否制御 | `lib/personaGuard.ts` | — |
| 人格定義 | `PersonaId` = `polite` / `gentle` / `concise` / `plain`（4 種） | — |
| 軸 | `formality` / `softness` / `density` / `directness`（4 軸） | — |
| UI | `Topbar` の persona トグル + 人格選択 | 初期値 OFF |

実装規模の実測値は **Appendix §7.6 PP-M-7** を正本とする。

### 2.2 何が判明したのか

〔Owner〕変換系を実装し、実際に大量の文章を生成して評価した結果、次が判明した。

- AI（およびルールベース変換）が文章を変換できること自体は成立した
- しかし生成された文章は、Owner が求める人格品質には到達しなかった
- そしてこの差は、**設計段階では予見できなかった**。実物を大量に見て初めて判明した

ここから得られた知見は、変換方式の優劣ではない。

> **実物を大量に評価する前に最終設計を確定させること自体が、この領域では危険である。**

設計を早く固めることは通常は美徳である。しかし人格品質のように「良し悪しの基準が実物を見るまで言語化できない」対象では、早期確定は**誤った基準を恒久化する**。

### 2.3 その結果、方式をどう変えたか

| | 研究した方式 | 現在の方針 |
|---|---|---|
| 生成タイミング | runtime（表示直前に機械変換） | **事前**（上位 AI で生成し、収録） |
| 品質保証 | 変換ルールの正しさで担保 | **人間が生成物そのものをレビュー**して担保 |
| アプリが持つもの | 変換規則 | **レビュー済み固定文章** |
| 最終設計の確定時期 | 実装前 | **実物評価後**（第3段階） |

### 2.4 現行 `PERSONA_PROFILES` の位置づけ

> **現行 `PERSONA_PROFILES` は、最終完成形としては採用しない方針となった機械変換方式の現行実装である。暫定機能・比較基準・検証資産としての扱いは別途判断し、直ちに legacy / deprecated / 削除対象とはみなさない。**

| 区分 | 内容 |
|---|---|
| **確定していること** | ・Persona Project の最終仕様ではない<br>・最終完成形として固定しない |
| **確定していないこと（＝いま判断しない）** | ・一周目または店舗検証時の**暫定機能**として使うか<br>・将来方式との**比較基準**として維持するか<br>・**検証資産**として保持し続けるか<br>・いずれ廃止するか、するならいつか |
| **現在の事実**〔実測〕 | ・runtime で稼働している（`Topbar` から到達可能。初期値 OFF）<br>・`module.persona` フィールドは参照していない（`PERSONA_PROFILES` 定数のみを使用）<br>・Lifecycle State を Legacy / Archived と判定した記録は存在しない |

**Disposition の判断時点は §7.4 が正本である。** 本節は位置づけのみを扱い、判断時点の一覧を複製しない。

**判断していないことを、判断済みとして扱わないこと。**「最終仕様ではない」から「不要」「廃止対象」を導かない（PP-NP-3）。

> 現在も有効な知見（PP-VA-1〜4）と、第2・第3段階で再利用可能性を評価する候補（PP-RC-A1〜A6 / PP-RC-B1〜B5）の詳細は **Appendix §2.5** を参照。

### 2.6 得た設計上の教訓

| ID | 教訓 | 一般化の可否 |
|---|---|---|
| **PP-L-1** | 良し悪しの基準が実物を見るまで言語化できない対象では、実物評価の前に最終設計を確定させてはならない | **一般化可能** → `docs/DESIGN_PRINCIPLES.md` **DP-16** へ昇格済み |
| **PP-L-2** | 「AI が実行できること」と「求める品質へ到達すること」は別問題である。実行可能性の確認は品質の確認にならない | 一般化可能（AI を用いる全機能に適用しうる） |

```
【第3段階】Persona Project 本実装
           base 凍結 → 上位 AI で約5人格を生成 → 人間レビュー → 収録
```

各段階の**移行は自動ではない**。前段階の完了条件を満たしたことを確認して初めて次へ進む。

### 3.2 第1段階 — 全 module の base 指導文完成（現在）

#### 3.2.1 base persona の定義

**base persona とは、人格変換の対象ではなく、変換の基準線である。**

| 要件 | 内容 |
|---|---|
| 医療的意味の正確さ | 指導内容として正しいこと |
| **全 module で同じ温度感** | module によって丁寧さ・距離感がばらつかないこと |
| 人格を強く乗せない | 特定の話し方に寄せないこと |
| 変換元となりうること | ここから人格別文章を生成できる状態であること |

現在 `bridges/*.md` に書かれ、PN1 で凍結され、canonical JSON の S / O / A / P に格納されている本文が base persona である。

> **用語の対応**: `docs/feature-glossary.md` §Persona の概念①「bridge 本文そのものの文体」が base persona に相当する。概念②（runtime 文体変換）・概念③（module JSON の persona フィールド）とは別物である。

#### 3.2.2 なぜ base が先か

**変換元が確定していない状態では、変換規則も生成物も設計できない。**

base 指導文が module ごとに温度感がばらついたまま人格変換をかけると、生成される差分は「人格の差」ではなく「base のばらつき」になる。それを人格別文章として固定すると、**ばらつきが仕様として恒久化する。**

これは測定の問題である。

> **基準線が動いている状態で差分を測ってはならない。**

base persona の要件「全 module で同じ温度感」は、人格の設計ではなく**基準線の定義**である。

#### 3.2.3 この段階の完了条件と、その射程

| # | 条件 |
|---|---|
| 1 | 対象 module の base 指導文が bridge に確定し、canonical JSON へ反映されている |
| 2 | 各 module が canonical 完成条件を満たす（`docs/JSON_STANDARD.md` JS-A 全 module 必須フィールドの充足を含む） |
| 3 | `module.persona`（接続枠）が全 module に一貫して存在する（§4.1 / §4.2） |

条件3が本文書の関心事である。**base 指導文の完成（内容）と、接続枠の一貫性（構造）は、同じ第1段階で並行して満たす。**

> **本節は Persona Project から見た第1段階の必要条件を定める。**
> 薬剤領域全体の一周完了、対象 module 集合、各 module の医学的完成判定は、それぞれ bridge・進捗管理文書・生成工程の正本に従う。
> **本書だけでアプリ全体の一周完了を宣言しない。**

### 3.3 第2段階 — Static 版の店舗実運用検証

#### 3.3.1 何を検証するか

〔Owner〕Static 版を自店舗で実運用し、次を検証する。

| 対象 | 検証内容 |
|---|---|
| SOAP 生成 | 実際の投薬業務で使える記録が出るか |
| UI | 操作上の不足・必要な追加機能 |
| 検索 | 目的の薬剤へ到達できるか |
| 多剤合成 | 複数薬剤同時選択時の合成が破綻しないか |

この検証は persona のためだけのものではない。**アプリ全体の実運用検証であり、その副産物として persona の要件が得られる。**

#### 3.3.2 この段階で persona を実装しない理由

| # | 理由 |
|---|---|
| 1 | **切り分け可能性。** 未確定の変換層を挟むと、不具合の原因が base にあるのか変換にあるのか判別できなくなる |
| 2 | **検証対象の汚染回避。**「SOAP が読みにくい」原因が base の問題か人格変換の問題か区別できなくなる |
| 3 | **要件の順序。** persona に必要な条件（変えてよい範囲）は、この検証の**出力**である。出力を入力にはできない |

#### 3.3.3 検証で確定させること

〔Owner〕この段階で次を確定させる。

| # | 確定事項 |
|---|---|
| 1 | **どの部分なら人格を変えてよいか** |
| 2 | **どこは医療的意味として絶対に変えてはいけないか** |
| 3 | persona UI に必要な条件 |
| 4 | 実運用上の不足機能 |

**なぜ机上で決められないのか**

医療的意味の不変条件は、抽象的な原則としては書ける（「医学的意味を変えない」）。しかし**実際に効く境界は、実運用で「この文をこう言い換えられたら困る」という具体形でしか露出しない。**

検証前に境界仕様を書くと、**実際には安全な変換を禁止し、危険な変換を許す**境界を引く。境界の精度が不足しているのではなく、**境界を引くための観測がまだ存在しない**という状態である。

現行実装が持つ保護境界（保護語句リストと非変換行の判定）は、この境界を機械的に表そうとした**現時点の暫定形**である。第2段階の観測は、この境界が十分か・過剰か・別の軸が要るかを判断する材料になる（詳細は **Appendix §2.5.3 / §2.5.4**）。

### 3.4 第3段階 — Persona Project 本実装

#### 3.4.1 base 凍結が前提条件である理由

§1.4 の制約 **PP-C-2** から導かれる。

| 方式 | base が変わったとき |
|---|---|
| リアルタイム変換 | 変換結果が自動的に追随する。**再作業なし** |
| **固定文章（採用方式）** | 当該 module の**全人格分を再生成し、再レビューする**必要がある |

約5人格であれば、base の 1 文修正が**5 倍の再作業**を生む。したがって「base 完成 → 凍結 → 生成 → レビュー → 収録」の順序は選択ではなく、**方式から導かれる必然**である。

これが「第1段階を先に終える」という判断の、最も直接的な根拠である。

#### 3.4.2 人間レビューの位置づけ

| ステップ | 主体 | 判定対象 |
|---|---|---|
| 生成 | 上位 AI | — |
| **検証** | **人間** | **医療的意味が一切変わっていないこと** |
| 収録 | — | **検証を通過した文章のみ** |

**検証を通過しなかった文章は収録しない。** レビューは形式的な確認ではなく、収録の可否を決めるゲートである。

#### 3.4.3 この段階で初めて決めること

**§0.4 に列挙した「決めないこと」の全 6 項目が、この段階で決定される。** 一覧は §0.4 を正本とし、本節では複製しない。

本段階固有の性質は次の 2 点である。

- 決定の入力は**第2段階の観測結果**であり、机上の設計ではない（§3.3.3）
- 決定は base の凍結後に行う。凍結前に決めても PP-C-2 により無効化しうる（§3.4.1）

### 3.5 段階別の決定権限

各段階で**決めてよいこと**を示す。決めてはいけないことの一覧は §0.4 を参照。

| 段階 | 決めてよいこと |
|---|---|
| **第1段階（現在）** | base 指導文の内容／canonical 構造の完成条件／**接続枠の存在と一貫性** |
| **第2段階** | 変えてよい範囲 / 変えてはいけない範囲／persona UI に必要な条件／不足機能 |
| **第3段階** | 上記に加え、§0.4 の全 6 項目 |

> **段階を飛ばして決めないこと。** 前段階の出力を入力とする決定は、前段階が完了するまで行えない。これは慎重さの問題ではなく、依存関係の問題である。

## 4. `module.persona` の現在の責務

### 4.1 予約枠としての位置づけ

> **現在の `module.persona` は、将来の Persona 接続点が全 module に存在することを保証する予約枠である。**
> **最終的な人格別固定文章の格納構造を確定するものではない。**

**枠を現在から保持するという判断**と、**現在の枠形状を最終仕様として固定するという判断**は別物である。本文書は前者のみを定め、後者は行わない。

現在の値の性質:

> 現時点の `module.persona` は、将来の人格別固定文章そのものを表すものではない。**PN5 で定められた中立的な予約値を保持し、全 module へ将来接続枠を通しておく役割**を担う。

値の出典は `prompts/vNext/PN5-Non-Scenario.md` の fallback 既定値である。bridge は persona の構造を定義しない（**Appendix §4.4**）。

〔Owner〕枠を保持している理由は runtime のためではなく、**二周目で型・Validator・canonical・UI を全部作り直さないため**である。先払い済みの経路と将来どのみち新規設計が必要な経路の区別は **Appendix §4.5** を参照。

#### 枠が確定しないもの

> 現在の枠は、最終的な人格数・人格別文章構造・UI・適用方式を確定しない。
> 現行の `PersonaConfig` と PN5 fallback による**暫定的な構造制約は存在する**が、第3段階で加算・移行・置換を選択できるため、これを最終仕様上の制約とは扱わない。

**完全に無制約であるとは書かない。** 暫定的な構造制約の存在は認めたうえで、それが最終仕様を拘束しないことを述べている。

### 4.2 Lifecycle State と Canonical Requirement

`module.persona` は**2 つの軸で位置づけられる**。両者は直交しており、一方が他方を決定しない。

| 軸 | 正本 | 値 |
|---|---|---|
| **Canonical Requirement** | `docs/JSON_STANDARD.md` **JS-A**（全 module 必須） | **必須**（完成 module では欠落を許容しない） |
| **Lifecycle State**（runtime 接続の段階） | `docs/DEVELOPMENT_STANDARD.md` §10 | **canonical field は Lifecycle 台帳の登録対象ではない** |

#### Lifecycle 台帳への登録単位

Lifecycle 台帳（`docs/DEVELOPMENT_STANDARD.md` §10.2 / §10.3）の登録単位は **機能 / 経路 / 実装資産**であり、canonical field 単体は登録しない。

| 対象 | 台帳登録 |
|---|---|
| `module.persona`（canonical field） | **登録しない**。Canonical Requirement 側（JS-A）が正本 |
| **Persona runtime connection**（将来機能） | Future Expansion の登録対象 |

#### Validator は Repository の仕様を決定しない

Validator の責務は、**既に正本で定義された仕様を、機械的・再現可能に検査すること**である。`module.persona` の必須性は **JS-A が定める**。`lib/moduleValidator.ts` の `MISSING_PERSONA` は**その宣言を機械的に担保する実装であり、新しい必須規則を追加するものではない**。

したがって次が成立する。

| 判定 | 根拠 |
|---|---|
| **runtime 参照数は `module.persona` の必要性の指標ではない**（PP-NP-1） | 参照数 0 は Lifecycle State の事実であり、Canonical Requirement を左右しない |
| **Validator の FAIL 可否を Lifecycle State は決定しない**（PP-NP-2） | 決定するのは Canonical Requirement である |

Validator が何を検査し何を検査しないかの詳細、および ERROR 分類の意味は **Appendix 第5章**を参照。

### 4.6 第3段階での再評価

現在の枠形状は暫定である。第3段階で次を判断する。

| 選択肢 | 内容 |
|---|---|
| **加算** | 現在の構造を保ったまま、人格別固定文章を格納するフィールドを追加する |
| **移行** | 現在の構造から別構造へ移す |
| **置換** | 現在の構造を廃し、新構造へ入れ替える |

**いずれになるかは現時点で決めない**（§0.4）。第2段階の観測と、第3段階で確定する人格仕様に依存する。

現在の枠が保証しようとしているのは次の 1 点である。

> **F-4b 完了後は、どの選択肢を採る場合でも、全 module が Persona 接続枠の存在要件と検証経路に組み込まれた状態から開始できる。**

**F-4b が完了するまでは、接続枠を持たない module が残る。上記は F-4b 完了後の状態を述べたものである。** また、**現在の枠形状が接続点として永続するとは断定しない。**

## 6. 誤解が繰り返される構造

> 個別の誤解（PP-NP-1〜PP-NP-5）に対する原因分析・実測による反証は **Appendix 第6章（§6.1〜§6.5）** が正本である。本章は構造的要因とまとめのみを扱う。

### 6.6 なぜこの誤解が繰り返されるのか

> **設計思想が到達経路の外に置かれ、到達経路上に反対方向の情報が存在すると、担当者は文書に忠実であっても誤った結論へ到達する。これは個人の誤読ではなく、情報構造によって再生産される。**

したがって、正本を作成するだけでは再発を防げない。**到達経路への接続と、補助情報の訂正が成立条件である。**

本 Repository でこの機構が成立していた実測上の内訳は **Appendix 第6章**を参照。

### 6.7 本章のまとめ

本書が扱った誤解は、担当者個人の判断ミスだけでは説明できない。

Repository 内で、

- 異なる時間軸の情報（現在の実装 / 将来の計画）
- 異なる概念の persona（bridge 本文の文体 / runtime 変換 / canonical field）
- Lifecycle State
- Canonical Requirement
- MEMORY
- 起動時必読文書

が**別々の経路へ配置され、一部では相互に矛盾していた**ため、同じ結論が制度的に再生産されていた。

> **本文書の目的は、新しい Persona 思想を発明することではない。**
> **既に存在していた Owner の設計思想と、Repository 内に分散していた根拠を、新規担当者が必ず到達できる形へ再配置することである。**

思想は bridge（13 件の `nearFuturePriority` / `futureExpansionPolicy`）・DP-13・JS-A・`docs/feature-glossary.md` の概念分離・PN5 の fallback 規定として、**既に Repository に存在していた**〔実測〕。欠けていたのは思想ではなく、到達経路と、思想どうしを結ぶ 1 枚の記述である。
